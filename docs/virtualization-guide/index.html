01 / AN INSTRUCTION

Begin with one instruction, not a virtual machine.

A CPU repeatedly finds an instruction, works out what it means, performs its work, and makes its result part of the program's visible state. Hardware virtualization does not replace that engine. It changes the conditions under which the engine is allowed to keep going.

Suppose a Rust program eventually executes the x86-64 instruction mov rax, [rbx]. The architectural story is short: read the address in rbx, load eight bytes from memory, put them in rax, and advance to the next instruction. The machine may actually fetch ahead, decode several instructions, execute work out of order, and consult multiple caches. Software normally sees the retired result: the point at which an instruction becomes architecturally committed. An instruction that was speculatively executed and then discarded did not retire.

RIP is the x86-64 instruction pointer: it names the instruction the architectural machine will execute next. RAX and RBX are general-purpose registers, fast named storage locations visible to software. An instruction can use register values without touching memory, or it can use a register as an address as our load does. A VM exit later reports a guest RIP so the hypervisor knows where guest execution stopped; that statement only makes sense once RIP has a concrete meaning.

“One instruction” does not mean “one clock cycle.” A cached addition may complete quickly; a cache miss may wait hundreds of cycles. A single REP string instruction can perform many element copies and may be interrupted and resumed partway through. Bedrock therefore cares about the exact architectural event it counts, while real elapsed time still depends on caches, memory and scheduling. The distinction between retired instructions and cycles is the basis of the whole performance story.

What a Rust pointer becomes on this machine

A Rust expression such as let x = *ptr; does not inherently mean one CPU instruction. The compiler chooses instructions based on type, optimization level, surrounding code and target features. For a simple 64-bit load, the machine may eventually execute a form like mov rax, [rbx]. The address in RBX is still a virtual address until paging hardware translates it. RAX is a destination register. If the access is permitted, the loaded value becomes visible when the instruction retires. If the mapping is missing, the CPU raises a fault and the load does not retire as a completed load.

This separation between an instruction's architectural meaning and its physical implementation will recur. Architecturally, an x86 load reads memory and changes a register. Internally, the core may look up a translation, search caches, speculate past a branch, wait for memory, or replay internal work. Hardware virtualization adds permission and intercept checks to this machinery. It does not require Bedrock to receive a callback for each successful ordinary load. Bedrock gets control only at events it configured, faults in the host-owned memory layer, or other architecturally defined exits.

One more x86 wrinkle matters later: the word “instruction” does not always imply a small fixed amount of work. A REP-prefixed string operation can copy many elements while retaining a single program-level instruction identity. Some instructions can be interrupted and resumed partway through their work. A safe deterministic execution plan must know what its counting and stop mechanisms mean around such instructions. This is one reason the AMD planner classifies REP sites as hazards instead of assuming every decoded instruction is a trivial one-step unit.

02 / INSIDE THE CORE

What happens underneath the instruction story?

An x86 instruction is an architectural promise. The physical core may carry it out through many internal steps, often overlapping with work from other instructions.

The processor fetches instruction bytes, predicts likely control flow, decodes x86 instructions into internal operations, schedules them when their inputs are ready, and eventually retires their architectural effects in program order. A cache hit can make a load fast; a miss can expose memory latency. A branch misprediction can discard speculative work. None of this changes the required final behavior of an ordinary instruction, but it changes how many wall-clock cycles pass before that instruction retires. That is why a program can retire the same instruction sequence in different elapsed time on two runs.

The retirement point matters to Bedrock because it separates visible progress from speculative effort that was discarded. A performance counter configured for retired instructions can approximate a logical execution coordinate. It does not describe the amount of work the CPU did internally: a mispredicted path may have used execution units and cache bandwidth without adding to the architectural count. For deterministic replay that can be acceptable if the guest-visible state and event schedule depend on retirements, while the host wall time remains variable.

Hypervisor performance has at least two cost sources. First is steady-state guest work: translating addresses, hitting caches, executing instructions and retiring them. Second is control-plane work: leaving the guest, saving or reporting state, running host code, changing controls and returning. Hardware virtualization makes the first source close to ordinary execution when it can run uninterrupted. It does not make the second source free. A workload with one exit per million instructions can be fast on either vendor; a workload with one exit per handful of instructions is likely dominated by transitions and host software.

There is no public, universal “VM exit costs N cycles” constant. Exit reason, CPU generation, state configuration, caches, mitigations and host handler all matter. The architectural manuals specify state transitions and controls; they generally do not reveal a complete transistor-level implementation. Where this guide draws a pipeline or cache box, it is an explanatory model of the contract and performance mechanisms, not a claim about the proprietary physical layout of an EPYC or Xeon core. [Intel SDM, AMD APM]

Front end, back end, retirement: three jobs with different costs

The front end finds instruction bytes and predicts which bytes are likely next. The back end schedules decoded work to functional units once inputs are ready. Retirement makes completed work architecturally visible in a valid order. A branch predictor helps keep the front end busy; when it guesses wrong, speculative work is discarded. A load may stall waiting for memory while independent later operations execute. From the program's point of view, the CPU still obeys the instruction set's required behavior. From a performance point of view, these internal choices can change cycles dramatically.

Different caches serve different things. Instruction caches hold code bytes. Data caches hold recently used data. A TLB caches address translations rather than the bytes themselves. Page-walk caches may retain intermediate paging information. None of these is a promise that a guest run takes the same wall time twice. A deterministic test uses a logical coordinate such as retired instructions precisely because caches and host scheduling can change the physical duration of the same visible execution. An instruction-retired counter measures committed instructions, not all speculative internal work or all memory traffic.

When a VM exit occurs, the core redirects execution to host context and the hypervisor handles it. The exact internal pipeline behavior is CPU-generation-specific and not fully exposed in vendor architecture manuals. Still, the broad cost model is clear: entry and exit involve state transition, validation and a change in what code is fetched; host code then performs its own reads, branches and writes. Frequent exits repeatedly pay that control-plane work. VPID/ASID and related caching aids can retain translations, but they cannot make a deliberately requested host handler run for free.

03 / CPU STATE

What state makes an instruction mean something?

The same instruction bytes can behave differently depending on the current register values, address space and privilege level. That context is CPU state.

General-purpose registers hold operands and results. RIP selects the next instruction. RFLAGS holds condition and control flags. Other registers have system-level jobs: CR3 points at the current top-level page table; other control registers enable paging and other processor modes. Software also uses model-specific registers, or MSRs, to configure hardware features such as performance counters. MSRs are not a bag of normal program variables: many require privileged instructions to read or write, and their meanings are defined by the CPU vendor.

Privilege adds a second axis. Application code normally runs with less authority than the operating-system kernel. On x86, CPL is the current privilege level; CPL3 is typical application code and CPL0 is the kernel. A normal application cannot rewrite CR3 or configure hardware counters at will. A system call deliberately switches from application code into the kernel. A page fault or interrupt also transfers control, but for different reasons.

Virtualization adds another axis, separate from CPL. Intel calls the hypervisor's mode VMX root and the guest's mode VMX non-root. A Linux guest kernel can be at its own CPL0 while still in non-root mode. AMD has an analogous host/guest split under SVM. The guest kernel has enough authority to manage its virtual machine, but the hypervisor retains control of actual memory ownership and selected hardware events. This is why “guest root” is not “host root.”

We will later see VMCS on Intel and VMCB on AMD. They are records holding guest state and control choices. Before seeing either, keep the simpler picture: entry loads a coherent context; exit gives the host a reason to inspect or change that context. [Intel SDM, AMD APM]

Which state belongs to a process, a guest, or the host?

In an ordinary process switch, Linux saves enough application registers to resume that process later and changes the active address space. A virtual-machine switch is broader: the CPU moves between host and guest execution modes and may also move selected control state. Some guest state lives in VMCS/VMCB fields; some is held in processor registers while the guest runs; some is saved or restored by host code. The architectural manual defines the exact division. A hypervisor cannot treat a VMCS or VMCB as a plain Rust struct whose fields automatically mirror every physical register at all times.

CR3 is particularly important because it changes the meaning of nearly every virtual address. If Bedrock approves code under one guest CR3 and the guest switches address spaces, the same RIP value might translate to different bytes. The AMD guarded-region planner therefore reasons about translation dependencies, not merely instruction addresses. By contrast, a general-purpose register such as RAX often holds a temporary result that changes many times per function call; it does not define a global address-space mapping.

MSRs control hardware facilities rather than ordinary computation. A PMU event-selection MSR can choose “instructions retired,” a counter MSR can hold the numeric count, and virtualization MSRs can configure entry or control features. The host must decide what the guest is allowed to read, write or observe. Intel's Bedrock path uses VM-entry and VM-exit MSR lists to move PMU state; the tested AMD path uses PMC virtualization. The goal is the same: guest count should reflect guest progress, while Bedrock's host instructions remain outside that guest logical clock.

04 / PROCESSES

An address belongs to an address space.

When a Rust program holds a pointer, its numeric value is usually a virtual address. Two processes can use the same number and still refer to different physical memory.

The operating system creates an address space for each process. Page tables are the data structure describing how virtual pages map to physical frames, along with access permissions. Switching a process typically changes which page-table root is active. In x86-64 that root is selected through CR3. This is why a raw pointer value is insufficient to identify actual RAM: its meaning depends on the current address space.

INTERACTIVE / TWO ADDRESS SPACES

The same pointer can reach different RAM

Process A has table A in CR3. Its load from 0x4000 reaches frame A2 and reads 0xAA. Switching the scheduled process changes the mapping, not the pointer's numeric value.

The page tables are simplified to one visible mapping each. The CPU uses the active CR3 root and can cache translations tagged to their address space.

For each memory access, paging hardware either finds a permitted mapping or reports a page fault, written #PF. A page fault is normally an event for the guest operating system: perhaps the page has not been allocated yet, perhaps it is a copy-on-write page, or perhaps the access is invalid. The OS may install a mapping and retry, or may terminate the process. Neither outcome inherently involves a VM exit.

Permissions matter independently of the address itself. A page can be readable but not writable, or non-executable so instruction fetch is forbidden. Those distinctions will later let Bedrock use the hardware as a guard: it can allow a data read while stopping a code fetch from a page whose behavior it has not yet proven safe. [Intel SDM, AMD APM]

Why the operating system gives processes separate address spaces

Separate address spaces provide isolation and a useful programming illusion. Process A can place its code, stack and heap at convenient virtual addresses without coordinating raw RAM locations with process B. The kernel maps those virtual pages to frames it owns and sets permissions. It may map a shared library into both processes, map a read-only file into many processes, or give each process a private writable copy. The same virtual pointer value can therefore mean different data under different CR3 roots, as the animation shows; conversely, two different virtual pointers can intentionally name the same physical frame.

On a context switch, Linux changes which process is running and which page-table root is active. The TLB may retain translations tagged by an address-space identity, but an entry must never be used under the wrong context. Virtualization does not remove this guest mechanism. Bedrock runs a Linux guest that schedules its own processes, changes guest CR3, takes guest page faults and manages guest virtual memory. The host owns a second, independent mapping from the guest's invented physical frames to actual host frames.

Copy-on-write shows why permissions are active machinery, not merely annotations. A parent and child can initially refer to the same physical page while both mappings are read-only. When one tries to write, a fault lets software allocate a private copy and update its mapping. Bedrock uses a related host-level copy-on-write technique for forked VM states. The guest's own page fault and the host's nested-memory fault are different layers of that story, and the performance cost depends on which layer catches a particular write.

05 / PAGE WALKS

How does a pointer reach RAM?

A virtual address does not contain a physical address. The CPU follows page-table entries to find a physical frame, checks permissions, and then adds the offset within the page.

For common four-level x86-64 paging, the virtual address is divided into several indexes plus a page offset. Starting at the root named by CR3, hardware reads a top-level entry, then lower-level entries, until it reaches a leaf mapping. With 4 KiB pages, the low 12 address bits are the offset. Large pages can stop the walk earlier. Each entry may restrict permission; a missing or forbidden mapping causes #PF. The CPU may perform parts of this walk speculatively, but the resulting access must satisfy the architectural checks.

A toy page table you can calculate by hand

To make the data structure tangible, imagine a tiny machine with 16-bit virtual addresses and 256-byte pages. The low eight bits of an address are the offset within its page. The high eight bits choose a virtual page. Suppose page 0x12 maps to physical frame 0xA0. Address 0x1234 then reaches physical address 0xA034: the mapping replaces the page number while preserving the offset 0x34. If page 0x1A maps to frame 0xB0, then 0x1A34 reaches 0xB034. Real x86-64 paging uses several levels and normally 4 KiB pages, but the frame-plus-offset operation is the same.

A page-table entry is therefore not merely an address pointer. It also carries flags. If the toy entry is read-only, a read succeeds but a write faults even though the translation exists. If no entry maps page 0x20, the CPU cannot infer a physical frame and raises a page fault. The guest kernel can respond by allocating memory, loading a page or rejecting the access. This is why a “page fault” can be part of normal demand paging rather than necessarily a bug. The next virtualization layer adds a second independent mapping after this guest translation.

A full walk can require multiple memory reads, so processors cache completed translations in a translation lookaside buffer (TLB) and may cache intermediate walk information too. A TLB hit avoids repeating the walk. This is a major reason why paging is practical at high speed. It is also why changing a page-table entry requires care: a stale cached translation must be invalidated before the new mapping can be relied upon.

Translation and caching are different questions. The page table says what mapping is authoritative. The TLB accelerates repeated use of that mapping. Later, Intel VPID and AMD ASID will be much easier to understand: they are tags that help the CPU distinguish cached translations belonging to different guest contexts. They do not grant permission, and they do not make a changed mapping magically current. [Intel SDM, AMD APM]

06 / FAULTS AND INTERRUPTS

Not every stop is a VM exit.

An exception, interrupt, system call and VM exit all redirect execution. They differ in who requested the redirect, when it occurs, and who handles it.

A system call is a program intentionally asking the kernel for a service. A page fault is a synchronous exception from a specific memory access. A hardware interrupt generally announces an external or asynchronous event. A VM exit transfers from guest execution to the hypervisor because a virtualization control or second-stage memory rule requires it. A guest can see its own page fault and handle it without the hypervisor emulating every step. Conversely, a nested-memory denial returns to the hypervisor even if the guest's own page tables would allow the access.

These boundaries compose. A guest application may execute a system call; the guest kernel then touches a page that the hypervisor has marked read-only; that second access may cause a VM exit. The hypervisor can modify the second-stage mapping and resume the guest kernel, which may finish the original system call. If we count every one of these as the same kind of “trap,” we lose the reason a particular workload is slow.

Bedrock's key performance counter is therefore the number of host returns caused by the virtualization boundary. A guest-internal page fault still costs guest work, but a VM exit also incurs a hardware world switch plus Bedrock's host-side bookkeeping. [Intel SDM, AMD APM]

What the CPU actually does on SYSCALL

On x86-64, SYSCALL is an instruction, not a library call to another userspace function. The application executes it with a syscall number and arguments arranged according to its operating-system ABI. The CPU saves a return instruction pointer and selected flags in architecturally specified registers, loads the kernel entry address from a privileged MSR, changes privilege state, and begins executing the kernel entry code. The kernel's entry assembly establishes a safe kernel stack and saves the register context it needs. Linux dispatches the requested operation, then returns through an appropriate instruction path so application execution continues at the saved point. This happens on the same physical core. The hypervisor does not need to emulate every syscall merely because the guest changed from CPL3 to CPL0. [Intel SDM, SYSCALL/SYSRET and privilege transitions, AMD APM, SYSCALL/SYSRET]

The stack detail is a good example of why a real control-flow diagram matters. The application stack belongs to userspace and cannot simply be trusted as a kernel working stack. The CPU's SYSCALL transition does not by itself create a complete high-level Rust call frame. The kernel entry code switches to its own stack, saves context, handles the service, and constructs the return. In the visual scene above, the highlighted kernel stack appears only after the core has crossed into guest-kernel execution. Bedrock still remains in the host lane, idle, unless a separate virtualization control trips.

A page fault is a retry point; a VM exit is a different boundary

Suppose the userspace instruction mov rax, [rbx] references an unmapped virtual page. The CPU's guest page-table walk cannot produce a permitted translation. It raises #PF, records the faulting address and fault information, and enters Linux's guest page-fault handler. The load has not retired. If Linux allocates or maps the page, returning from the handler retries the same instruction at its original RIP. If the address is invalid, Linux may signal or terminate the process. The same guest-internal exception mechanism also handles many copy-on-write page faults. None of this necessarily crosses into Bedrock.

Now suppose the guest page table permits the access, but Bedrock's EPT or NPT mapping denies it. The denial belongs to the second-stage translation. Hardware exits to the host and reports a nested-memory failure. The guest Linux page-fault handler does not initially receive this event, because its own mapping was valid. Bedrock may use the host return to maintain copy-on-write state, catch a code write or build a safe execution region. It then resumes the guest, often at the same RIP so the stopped access can retry after the host has changed its mapping. This is why the memory scene shows the two permission layers separately.

An interrupt is a delivery decision, not an instruction request

A hardware timer or virtual device can make an interrupt pending independently of the guest's next instruction. The CPU may deliver it when architectural conditions allow, saving the interrupted context and entering the guest handler. Linux then runs its timer and scheduler code. A deterministic test cares about exactly which guest instructions retired before delivery. Bedrock controls the virtual event schedule and must stop guest execution at the intended logical boundary before making the timer visible. The underlying CPU may have efficient interrupt-delivery hardware, but “efficient” is not the same as “delivered at Bedrock's chosen retired-instruction count.”

These paths can nest. A guest application may execute SYSCALL, the kernel may take a guest page fault while copying an argument, and a virtual timer may become pending before the syscall completes. Bedrock's job is not to replace Linux's normal exception machinery. It is to control the host-visible boundaries and outside inputs so that this nested history can be reproduced. When we discuss performance later, we count VM exits separately from work Linux performs within its guest mode.

07 / VIRTUALIZATION

A VM is a different execution mode, not an interpreter.

Imagine a Rust function calling into code it does not control, while the CPU promises to return on certain operations. The guest's instructions still pass through the same decoder, execution units, caches and branch predictor as ordinary code. The extra machinery is a control plane: it decides which instructions or events transfer control back to the host.

Intel calls the two modes VMX root and VMX non-root. AMD calls the guest mode SVM guest and the transition VMRUN. These are orthogonal to rings: a guest kernel can run at guest CPL0, while the host kernel remains in control. The CPU loads guest state on entry and records exit state and reason on exit. Intel stores controls and state in a VMCS; AMD uses a VMCB. Each contains guest registers, intercept controls, nested page-table root and event-delivery state. [I1, A1]

Conceptually, a VM exit resembles an expensive callback across a hardware boundary. The processor switches a defined set of state, performs checks, and reports why control returned. Bedrock then runs host code to update its deterministic model before entering again. The important performance variable is therefore how often the callback happens. A million native instructions between exits can be cheap; one exit per instruction cannot be. That is why “hardware virtualization” alone says almost nothing about application speed.

What is under the hood?

Controls are consulted by CPU hardware during guest execution. Many ordinary instructions need no hypervisor work. Intercepted instructions or events cause a VM exit before or after an architecturally defined point; the exact point matters for replay. Host and guest share much of the physical microarchitecture, so cache and TLB state, speculation and host scheduling still affect wall time even when guest-visible results are deterministic. The VMCS/VMCB are control structures, not software emulators of a CPU.

The control structure is a contract with the CPU

Think of VMCS and VMCB as low-level configuration objects whose fields the hardware interprets. Some fields describe the guest's architectural state—RIP, control registers, segment state and interruptibility. Others tell the CPU which operations should return to the host. On exit, the processor supplies a reason plus qualification data: for example, an attempted nested-memory write and its address. The host must decide whether to emulate the instruction, change permissions, inject an exception or resume at the same RIP. A mistaken choice can alter guest-visible ordering even if final register values look reasonable.

The transition is not a Linux scheduler context switch. VM entry/exit saves and restores a specified subset of machine state and performs validation; the host's Rust/C/assembly path handles the remaining state and calls Bedrock's dispatcher. VM-entry MSR lists on Intel and PMU autoswap on AMD let hardware perform some state movement while keeping host work out of the guest's instruction count. Making one entry cheaper helps, but cannot compensate for tens of millions of avoidable entries. [I1, A1, B3, B6]

08 / WORLD SWITCHES

A VM exit is a boundary crossing with work on both sides.

The CPU reports a reason and changes execution context. Bedrock then decides what that reason means and what guest state should exist when execution resumes.

Consider a guest executing RDTSC under an intercept. The CPU reaches the instruction and transfers to the host according to the virtualization controls. The host handler reads the exit reason, calculates Bedrock's virtual time, places the result into guest-visible registers, advances the guest RIP as required, accounts for execution, and prepares another entry. The hardware world switch and the software handler are separate costs. Now consider an NPT or EPT write denial. The guest instruction has not completed its write, so Bedrock may need to inspect the address, make a copy-on-write page, temporarily relax permission or emulate the access, update proof state, and resume at the instruction to retry it. The correct RIP treatment differs from the RDTSC case.

Follow the VM-exit scene to watch the core cross into Bedrock. The memory scene shows why a stopped write retries while a completed clock-read intercept advances. The exit reason determines which kind of resume is correct.

A host/guest transition also changes which CPU state is active. Some state is managed by the VMCS or VMCB, some by entry/exit MSR facilities or PMU virtualization, and some by Bedrock's own code. Hardware may need to validate the guest state it is asked to load. Address translations may be retained under tags or invalidated after changes. The host also pays ordinary instruction and cache costs while it classifies and handles the exit. The cumulative cost is roughly exits × average total exit path, but the average can shift when an optimization changes which exits occur.

For a Rust engineer, one useful analogy is an FFI boundary with a dynamic handler and a kernel-mode context transition, but the analogy has limits. An exit can happen because of hardware permission checks or a pending event, not merely because guest code called a function. The CPU decides exactly which architectural work has happened before the exit. Bedrock must match that boundary when it emulates, retries or injects events. Mistaking a pre-instruction fault for a post-instruction trap can duplicate or skip visible work.

Most conventional VM optimizations try to reduce exits: shadow devices, paravirtualized I/O, tagged translations and interrupt-controller assistance. Bedrock intentionally asks for some exits to obtain deterministic time and guard its execution proofs. An optimization is therefore valuable only if it removes a class of repeated exits without losing the control needed for replay. The AMD profile in this repo is a good example: 42.8M exits are dominated by nested-page faults and clock reads, not a generic failure of AMD-V to execute instructions quickly. [Bedrock exit profile]

Follow one host return as an implementation exercise

On Intel, the host first chooses VMCS execution controls, an EPT root, guest state and host exit state. On AMD, it configures the analogous VMCB areas, NPT root and intercepts. When an exit condition occurs, hardware does the architecturally specified state transition and reports why control returned. This transition is not a Linux process switch: the guest and host are separate virtualization contexts, and the host must maintain virtual-machine invariants before re-entry.

Bedrock's handler can be thought of as a dispatcher with strict preconditions. It first classifies the exit. If it is a clock read, it must return the virtual TSC value and advance the guest past the instruction. If it is a denied code fetch, it must not pretend the instruction already ran; it must arrange permission or choose a fallback, then retry. If it is a guarded write, it must invalidate the proof depending on those bytes before letting them change. If it is a deadline stop, it must account for exactly how many guest instructions retired and decide whether the event is ready. These are different state machines, even if the top-level VMRUN/VMRESUME loop looks similar.

After handling an exit, the host prepares entry state. That can include counter reloads, pending-event injection, refreshed page permissions, breakpoint registers and cached proof validation. It may also need to flush translations after changing NPT or EPT. Only then does it execute the architecture's guest-entry instruction again. A profile that says “entry preparation consumes 37.1% of recorded cycles” includes substantial software work in this phase; it does not mean the hardware VMRUN or VMRESUME instruction alone costs that fraction. [AMD full-run profile]

This sequence explains why optimizing a single assembly instruction is rarely enough. If a workload exits 42.8M times, even a modest Rust planner cost repeated at every re-entry can dominate. Conversely, broadening an executable region may save NPFs but require more expensive proofs and more false breakpoint hits. The total wall time depends on the sum across all paths. We will use the measured exit ledger later instead of treating every exit as identical.

09 / TWO TRANSLATIONS

There are two owners of memory translation.

Inside Linux, a virtual address is translated by guest page tables to a guest-physical address. The host then translates that guest-physical address through EPT on Intel or NPT/RVI on AMD to a host-physical address. Hardware combines these walks and caches translations in TLBs. A guest page fault (#PF) and a nested-page fault (EPT violation / NPF) are different: the former belongs to Linux; the latter returns to Bedrock. [I1, A1]

EPT/NPT are more than isolation mechanisms here. Bedrock deliberately changes nested permissions to make the CPU an execution guard. An NX code page stops before its first instruction; a read-only code page stops a guest write that could invalidate a decoded proof; a read-only guest page-table frame stops a remap that could redirect execution. Bedrock checks the stopped access, revises its proof, and resumes. This is the core of AMD's guarded multi-instruction execution. [B4]

Changing a nested mapping is not just a store into a page-table structure. The processor may have cached an older translation. The VMM must invalidate or retag affected translations with the architecture's TLB-control mechanisms. Intel VPID and AMD ASID can retain translations across ordinary guest/host transitions, but neither licenses reuse after a mapping changes. Bedrock must also distinguish a virtual alias—two guest virtual addresses reaching the same hazardous physical code—from the physical page. NPT controls the physical page's execute permission; an execution breakpoint matches a linear address. A proof must cover the aliases that can execute. [I1, A1 §15.16, B4]

AMD's ROGPT changes a subtle but decisive detail. Without it, a guest page-table walk is treated as a nested write even when the walker only reads a page-table entry, so making guest tables read-only can create NPFs on ordinary translations. With ROGPT, walks request nested write permission only when the hardware must update accessed/dirty bits. On a same-box Linux boot/fork ablation, this difference moved the run from 18.49 seconds and 1.16 million exits to 213.45 seconds and 122.55 million exits. That is a feature dependency of this Bedrock guard design, not an intrinsic AMD-V versus VT-x speed ratio. [A1 §15.25.5, B1]

10 / CACHED TRANSLATIONS

Why VPID and ASID exist.

Every guest-to-host switch is potentially bad news for cached address translations. A tag lets the processor retain entries for different address spaces without confusing them.

Imagine the TLB holds a translation for guest virtual address 0x4000. The host also uses 0x4000, and another guest may use it for something else. Without a way to distinguish them, the processor would need to flush more cached entries at a switch. Intel's VPID and AMD's ASID attach an identity to guest translations so an entry can be reused only in its proper context. This is a performance mechanism for translation reuse; it does not authorize any access by itself.

Now suppose Bedrock revokes execute permission for a guest-physical code page. Updating an EPT or NPT entry changes the authoritative rule, but a CPU may still possess a cached translation reflecting the old rule. The hypervisor must perform the architecture-appropriate invalidation before relying on the page to fault. A tag helps keep unrelated entries across ordinary transitions; it is not a substitute for invalidating a changed mapping.

Intel supplies invalidation operations such as INVEPT and INVVPID, with scopes defined by the SDM. AMD supplies TLB-control mechanisms and ASID management described in its SVM chapter. Those names matter in implementation work; the invariant is simpler: after Bedrock tightens a guard, no old cached permission may allow the guest to pass it. The cost of maintaining this invariant can matter, but it is usually less important than eliminating millions of deliberately induced faults. [Intel SDM, AMD APM]

A second subtlety is aliasing. Two different guest virtual addresses may reach the same guest-physical code page. A nested page permission applies to that physical page. A hardware execution breakpoint applies to a linear address. If the same instruction can be reached through two virtual aliases, proving a breakpoint covers one alias is insufficient. Bedrock's AMD planner must account for reachable aliases when it grants execute access.

What a tag can preserve, and what it cannot

A TLB entry is approximately a cached answer to “under this address-space context, what physical destination and permissions correspond to this virtual page?” The exact internal structure is vendor- and model-dependent, but the correctness requirement is universal: an entry belonging to process A or guest A must not be mistaken for an entry belonging to another context. Tagging supplies an identity so hardware can retain more entries without flushing everything on each switch. Intel calls its guest tag a VPID; AMD calls the SVM guest identifier an ASID.

That identity is not a version number for every page-table entry. Suppose the host changes a nested page from executable to non-executable while the same guest tag remains active. An old cached executable translation could still exist. The host must use the architecture's invalidation mechanism or another documented transition that makes stale entries unusable. Only then can Bedrock rely on the next fetch faulting. This is an important correctness step for an execution guard: the page-table store alone is not the barrier the algorithm needs.

There are two kinds of reuse to keep separate. A guest process switch can change guest CR3, affecting guest virtual translation. A hypervisor NPT/EPT edit can change the host-owned second stage even if guest CR3 stays fixed. Hardware may cache combined translations and intermediate paging information. The invalidation required for one change is not necessarily the same as for the other. Bedrock's code must follow the vendor's rules for its chosen operations, rather than just clearing a software cache in Rust.

Tagging often improves conventional VM performance because guest/host transitions otherwise threaten useful translation state. But the AMD DST profile's 21.8M nested faults are largely requested by Bedrock's guard design. A VPID or ASID cannot transform a permission denial into a permitted access. It may reduce the cost around each transition, while the larger opportunity is to prove a safe region that needs fewer transitions at all. That is why these features appear in the guide as important but secondary to exit frequency for this workload.

11 / COUNTERS AND DEADLINES

A counter can tell you how far you went. It may not stop you exactly there.

The processor has a performance-monitoring unit, or PMU, with counters for events such as instructions retired. Bedrock needs both a count and a way to regain control near a selected count.

A performance monitoring counter (PMC) is hardware state that increments when a configured event occurs. Retired-instruction events are useful for a logical clock because discarded speculative work does not become guest-visible progress. A cycle counter measures something different: core time, affected by frequency, stalls and other execution details. The TSC is a clock-like CPU register; a guest can read it with RDTSC or RDTSCP. Bedrock intercepts those reads and returns a deterministic virtual value instead of exposing raw host time.

Program a counter, then watch what it actually promises

A PMU usually has a selection control and a numeric counter. Software chooses an event such as retired instructions, enables counting, and may load a starting value that will wrap after a desired number of events. The CPU increments the counter when matching events occur. At overflow, hardware can set status and request a performance-monitoring interrupt (PMI) or another notification path. This gives software a useful approximate alarm without forcing a host exit at every instruction. The architectural event and the notification are different stages.

In a virtual machine, the host must also decide whose instructions the counter counts. PMU events are also model- and feature-dependent. A processor might advertise a general counter but not the specific virtualization behavior Bedrock requires. Different core types can have different event support. Linux may reserve or configure counters on behalf of its own perf subsystem. Why not set the retired-instruction counter to overflow exactly at instruction 100,000 and inject the timer then? The counter event and the point at which software handles its interrupt need not coincide. The guest may retire additional instructions while the notification travels through hardware and interrupt delivery. That delay, called skid in this context, varies with hardware and workload. An ordinary PMU interrupt can therefore announce that a boundary was crossed without giving a safe, exact boundary to inject a deterministic event.

One expensive exact method is single-stepping: ask the CPU to exit after each instruction, inspect the count, and enter again. Intel's monitor-trap flag (MTF) is one such mechanism; the AMD implementation uses an equivalent synthetic stepping path for short fallbacks. Each step adds a host transition. Stepping a few instructions is fine. Stepping millions makes hardware virtualization slower than an interpreter because the host is entered over and over.

Intel's implementation uses PEBS to get very close to a deadline and then steps only a short final interval. AMD's implementation uses a virtual-PMU overflow notification plus a guarded executable region and a safety margin. Neither path is simply “the PMU counts instructions”; each needs a reliable stop and accounting across host/guest transitions. [Bedrock Intel counter, Bedrock PEBS, Bedrock AMD PMU]

12 / REPLAY BOUNDARIES

Why stop at instruction 100,000 instead of “about now”?

A deterministic test controls the order in which the guest sees time, interrupts and outside input. Delivering the right event a few instructions late may produce a different execution.

Imagine a guest thread holding a lock. A timer should arrive just before the instruction that releases it. If the timer instead arrives just after the release, the scheduler may run a different thread first. The final state might coincidentally match in a simple test, but the execution history and race exposure have changed. Bedrock therefore needs a logical coordinate for events. It uses retired guest instructions as the principal execution clock, then emulates time reads and manages idle offsets so guest-visible time is derived from controlled state rather than from host frequency or scheduling delays.

Determinism requires more than a counter. External inputs, device responses, random bytes, interrupts, process forks and time reads all need controlled behavior. There are several tempting shortcuts that fail this contract. Passing through the host TSC is fast, but the host clock advances during descheduling and can differ between runs. TSC offset and scaling alter the number a guest sees but still tie it to physical time. A regular wall-clock timer can interrupt after the guest retires a variable number of instructions. A PMU overflow tells Bedrock that a count was reached, but software notification may arrive after more instructions retire. Each shortcut may be acceptable for an ordinary VM and unsuitable for a deterministic replay boundary.

Once a near-exact stop is available, Bedrock can let large regions run directly on the CPU and regain control only when necessary. That is the performance ambition shared by the Intel and AMD backends. Their difficulty is not “can the core execute guest code?” Both can. The difficult question is “can we bound what runs, know how many guest instructions retired, and regain control soon enough to inject the next event at exactly the right point?”

13 / THE DST CONTRACT

Virtualizing a CPU is easier than making time repeat.

A conventional VM can let the guest see some real hardware timing. A deterministic test VM cannot: two runs must deliver the same guest-visible inputs at the same logical point despite different host scheduling, caches and CPU frequencies.

Bedrock uses retired guest instructions as the main logical clock. Its emulated TSC is based on that count plus explicit offsets when the guest is idle. It intercepts RDTSC and RDTSCP, returns the emulated value, controls random sources, emulates devices and uses copy-on-write forks to replay from a common state. The fork can test a different schedule or input while starting from equivalent memory. A patched Linux guest routes kernel randomness through a Bedrock hypercall; other guest patches shape clock and scheduler behavior. [B2, B7, B8]

The hard part is stopping at a specific instruction count. Suppose a timer must become visible at logical count 100,000. If the guest runs to 100,100 before the hypervisor notices, injecting the event then changes which instructions ran before the interrupt. Counting exits or using wall-clock timers cannot guarantee the desired boundary. A PMU overflow can announce that a count has been reached, but ordinary performance interrupts arrive after variable delay. Bedrock needs a way to stop before or near the boundary and then finish exactly. The original Bedrock article develops this timing problem; the next sections show the implementation that grew around it. [P1]

Determinism has a boundary.

Hardware still runs at real, variable speed. Bedrock makes the guest observe a controlled clock and controlled external inputs. “Same guest-visible execution” and “same host wall time” are separate claims. Exactness also depends on CPU-specific retirement semantics, guest patches, event delivery and proof invalidation; passing replay tests is evidence for the tested configurations, not a universal x86 theorem.

What has to be the same in a replay?

Imagine two workers that race to acquire one lock. Repeating their program bytes is not enough to repeat the winner. The relative order of their runnable periods, a timer interrupt, an incoming packet, or a returned random value can change the state at which either worker attempts the lock. A deterministic system therefore needs a rule for when each external influence becomes visible. In Bedrock, the central coordinate is the number of guest instructions retired. If an event was delivered at guest count N in the first execution, replay must arrange delivery at the equivalent logical boundary, even if host wall time or cache warmth differs.

The count is a coordinate, not a complete replay log. The initial RAM image, CPU state, disk and device contents, number of virtual CPUs, guest-visible feature set, and all injected inputs also matter. If one fork starts with a different page-table entry or a different CPUID result, both may retire the same number of instructions while reaching unrelated states. Bedrock's copy-on-write fork gives variants a common starting snapshot. Its device and randomness boundaries turn external observations into controlled values. A test campaign can then vary a schedule or input deliberately and know which change it introduced. [B7, B8]

Why a time read is an input, even though no one sent a packet

Consider an application that calls clock_gettime, checks whether a retry deadline has passed and chooses a branch. If the returned time depends on the host's current clock, a cache miss or a host preemption can change that branch on replay. The application can observe that difference even when the guest's memory and instruction stream were initially identical. Bedrock therefore controls the guest-visible clock, including direct RDTSC and RDTSCP reads where they are intercepted. Its logical clock is derived from retired guest work, with explicit treatment for time spent idle. A Linux system call that reads a clock is still a guest-kernel operation; it only becomes deterministic if the clock source that kernel consults is controlled too. [B2]

A boundary must also be precise. Suppose a timer is due after instruction 100,000, and a worker releases the lock at instruction 100,002. Delivering the timer at 99,998 and 100,003 produces different legal schedules. “A counter eventually interrupted us” does not guarantee the same ordering. This is why the vendor sections spend so much space on the hardware route from a counter event to an actual host stop. The exactness requirement is imposed by replay semantics; the PMU and virtualization features are tools for meeting it.

What deterministic execution does not promise

A deterministic schedule does not make a buggy program correct, nor does it imply that every possible schedule has been explored. It makes an execution reproducible under the controlled inputs and CPU model. DST uses that property to explore chosen alternatives and replay a failure. It also means a performance result must be interpreted carefully: a 180-virtual-second campaign can finish in less or more than 180 host seconds because virtual time and host time represent different things. The user-facing comparison later in this guide is between equivalent Bedrock campaigns, with their guest assets and host hardware called out, rather than a ratio between a virtual duration and a wall-clock stopwatch.

14 / A DST SYSTEM

What does a DST hypervisor give an application?

The application is still a normal guest program using Linux services. The deterministic test system controls what the program can observe from outside its own execution.

Picture a service test that starts several processes, opens sockets, reads the clock, asks for random bytes and waits on timers. Native execution lets the host OS and real hardware choose many observation points. A deterministic test instead needs a controlled schedule and input stream, so a failing run can be reproduced from the same initial state and choices. Bedrock supplies a Linux guest, virtualized devices, a logical clock and forkable memory state. The guest is not a binary translator: application and kernel instructions usually run on the physical CPU. The hypervisor intervenes at selected boundaries to make the outside world controlled.

Where the application actually spends time

If the service performs CPU work or memory access inside a stable approved region, hardware executes it directly, so that interval can be fast. If it calls the clock frequently, crosses many code pages, performs many device operations or triggers copy-on-write writes, the hypervisor runs more often. The slowdown is the sum of those interactions, not a fixed tax on every Rust instruction. This is why the exact guest kernel and image matter for a fair Intel/AMD test. Bedrock can shape some guest behavior through CPUID and patches, but a benchmark on one guest image cannot be attributed entirely to the host CPU. The clean performance question is still practical: with the workload Tempo actually cares about and an equivalent guest, how quickly do the two Bedrock backends complete and pass the deterministic test?

15 / INTEL ARCHITECTURE

VT-x supplies the trap surface; PEBS supplies a near-exact clock stop.

First, what VT-x actually adds

Without virtualization, a kernel at CPL0 can configure page tables and many CPU facilities directly. To run that kernel as a guest, the host must let it do ordinary work at full speed while retaining authority over physical memory and selected events. Intel's VMX extension provides two execution modes: root for the monitor and non-root for the guest. Both modes have privilege rings. A guest at non-root CPL0 behaves like a kernel to its applications but remains subject to VMX controls. This is the central separation: the guest owns a virtual machine; the host owns the actual machine.

The host enables VMX on a logical processor with VMXON, creates a VM-control structure, and enters a guest with VMLAUNCH or resumes it with VMRESUME. These are not a software interpreter loop for every guest instruction. Hardware reads control fields, establishes guest state and lets ordinary instructions flow through the processor. The guest may then run millions of instructions before any configured exit occurs. On a VM exit, hardware records an exit reason and transfers control to a host entry point. The host interprets that reason, edits state or controls, and enters the guest again. [Intel SDM, VMX chapters]

The VMCS is a structured agreement

The VMCS is a CPU-defined record that the host configures. It includes guest state such as the guest's RIP, control registers and interruptibility; host state for where an exit should land; control bits choosing what exits; EPT and VPID configuration; and fields where hardware writes the reason for an exit. It is tempting to picture a VMCS as a complete CPU snapshot, but entry/exit behavior is defined field by field. The host software still has to manage any state that the architectural transition does not handle automatically. A failed entry can arise from invalid state or controls, so a hypervisor must validate the contract it asks the CPU to execute.

Consider guest RDTSC. A VMCS execution control can request an exit on that instruction. The processor reaches it, exits to Bedrock, and reports enough information for Bedrock to return a virtual time value to the guest and advance past the instruction. By contrast, a plain integer add needs no host intervention. Consider an EPT write denial: the CPU is trying to satisfy a memory access, finds that the second-stage mapping forbids it, and exits with an EPT-violation reason and qualification. Bedrock may change permissions and resume at the same guest RIP so the access is retried. These two cases require different handling even though both are VM exits. [Intel SDM, VMCS and VM-exit information, Bedrock time exit]

EPT is a second authority over memory

Inside the guest, Linux still maintains its page tables. The CPU first interprets a guest virtual address through those tables to obtain a guest-physical address. Extended Page Tables (EPT) then translate that guest-physical address to actual host physical memory and check second-stage permissions. A guest page fault belongs to Linux; an EPT violation belongs to the host. This is both an isolation boundary and a useful interception surface. Bedrock can mark a page read-only to catch writes that would invalidate replay state or a code proof. It can deliberately deny a PEBS record write to turn a profiling event into a near-deadline exit.

EPT is a hardware-assisted walk, but a miss is not free: translating a guest virtual address may require reading both guest and EPT paging structures. Translation caches hide much of this cost in typical workloads. Intel's VPID identifies guest translation contexts, and EPT has its own invalidation operation. Neither eliminates the work caused by deliberately denying access: if Bedrock wants an EPT violation, the guest really must return to the host. [Intel SDM, EPT and VPID]

How Intel counts guest progress

Bedrock wants an instruction-count clock, not a wall-clock timer. Intel's performance monitoring unit can count retired instructions in a programmable counter. This repo configures IA32_PMC0 for INST_RETIRED.ANY_P. It saves the guest count on VM exit and reloads it on VM entry through VMCS MSR save/load facilities, so instructions executed by the host while handling an exit do not contaminate the guest logical count. This is a concrete example of hardware state movement doing useful work during entry/exit. It also imposes a feature and core-type assumption: the configured event must be available on the selected CPU. [Bedrock instruction counter]

An MSR list is a list of model-specific register/value pairs the CPU processes as part of entry or exit. In this design it helps keep guest and host PMU state separate. It does not remove all entry cost: the processor still validates state and crosses modes, and Bedrock still runs host code. But it avoids counting host instructions as if they belonged to the guest and avoids a software write for every piece of PMU state. The list must be staged in the right order; enabling a counter before its event and reload are ready would count the wrong interval. [Bedrock counter, Bedrock PEBS staging]

Why PEBS changes the deadline problem

Intel Precise Event-Based Sampling (PEBS) is designed to record information near a sampled event. Ordinarily a profiler arms a counter; when the event occurs, the processor writes a record into a buffer and eventually notifies software. Bedrock uses an unusually useful interaction on CPUs with the required EPT-friendly PEBS support: it places the PEBS record buffer in a guest page that EPT allows to read and execute but forbids writing. When hardware tries to write a PEBS record, EPT denies that write and causes an exit near the overflow point. The path bypasses the long, variable software interrupt delivery path that would make a plain PMI unsuitable as an exact stop. Bedrock does not need the record contents; it needs the denied write as a timely signal. [Bedrock PEBS implementation, Intel SDM, PEBS and EPT-friendly PEBS]

What other Intel features can and cannot buy

VPID helps retain tagged translations across guest/host transitions. APIC virtualization features can reduce exits in many conventional VMs. TSC offsetting and scaling can present a shifted or scaled hardware clock. The VMX preemption timer can force an exit after a hardware-time interval. Each may be useful in the right design, but none by itself implements Bedrock's instruction-count deadline or deterministic event ordering. A hardware-time timer drifts relative to retired instructions when the guest stalls or the host is descheduled. A scaled TSC still advances with host time rather than with Bedrock's logical count. For this workload, the high-leverage Intel combination is counting guest retirements and using the PEBS/EPT interaction to recover control near a chosen count. [Intel SDM, Bedrock PEBS]

A concrete Intel run, from an application load to the next timer

Start with Linux and a userspace process already resident in Bedrock's guest. The host has configured VMX, a VMCS, an EPT root and a guest instruction counter. It enters the guest. The userspace process loads a word from memory. The CPU checks the guest page tables and EPT, finds permitted translations in its caches or walks them if necessary, reads the data, and retires the instruction. The VMCS does not cause a host callback for this ordinary load. The counter advances because a guest instruction retired. This is the common case that makes a hardware VM fast.

Next the program calls into Linux with a system call. That is a guest-internal privilege transition. Bedrock need not handle the call as a VM exit merely because the guest moved from CPL3 to CPL0. Linux may change its own page tables, block a thread or return. If those actions touch a page or instruction that Bedrock has explicitly guarded, a configured exit can still occur. The key is that VMX mode and the guest's own privilege changes are independent.

Now suppose Linux or the application executes RDTSC. Bedrock asks VMX to intercept that instruction. On exit, it can compute virtual TSC from the logical retirement count and deterministic idle state. It writes the emulated result into the guest registers and resumes after the time-read instruction. A physical TSC read would be cheap but would leak host scheduling and speed into the guest's clock. On the profiled AMD workload, clock reads are a huge source of host returns; the same logical issue exists on Intel, even though the timing data here do not include an equivalent Intel exit ledger. [Bedrock clock exit, AMD exit profile]

Finally a virtual timer is due at guest instruction count 100,000. Bedrock cannot inject it when the host wall clock reaches an approximate point; the guest might have retired a different number of instructions. It sets up fixed-counter PEBS to fire before that count. The CPU runs guest work until PEBS attempts its record write into the specially protected guest page. EPT denies the write, creating an EPT violation. Bedrock recognizes this particular violation, reads progress, then uses MTF for the remaining short interval. At the exact logical boundary it injects the timer according to its deterministic schedule. The record buffer is a control surface, not an application data log. [Bedrock PEBS]

What the CPU maintains automatically, and what Bedrock still owns

VMX hardware enforces guest/non-root mode, checks configured intercepts, performs EPT permission checks, captures exit information and transfers to the host state named by the VMCS. The host owns the guest's virtual devices, event schedule, emulated time, memory sharing, and interpretation of every exit it requested. Even the PEBS trick relies on host preparation: Bedrock registers a scratch page, arranges its EPT permissions, configures fixed-counter and PEBS MSRs, handles a very specific EPT write violation, and finishes the deadline. Hardware provides the trap semantics; the software constructs the deterministic meaning.

It is useful to distinguish architectural state from microarchitectural state. The VMCS describes what guest state is loaded and what intercepts apply. Caches, branch predictors and translation buffers are hardware resources whose detailed implementation varies. A VM entry does not turn the processor into a fresh, deterministic physical machine. Bedrock's replay contract concerns guest-visible execution and controlled inputs, not identical cache-hit patterns or host wall time. This is why a near-native guest loop can coexist with variable benchmark timing.

The Intel stop has two nested margins

First, PEBS must be armed early enough that its EPT fault is observed before the event's logical deadline. The code has a minimum arming distance and a configurable margin. Second, after the exit, the remaining distance must be short enough that MTF stepping is affordable. These are not free constants that transfer to all CPUs. The feature check ensures the required PEBS format and EPT-friendly behavior; a measured margin on a tested server still needs validation for a new generation or core type. Bedrock's fallback handles a deadline too near to arm, but repeated fallbacks would worsen performance.

Why use fixed counter 0 for PEBS and PMC0 for the running clock? The code separates the trigger counter from the accounting counter. A counter that is reloaded to overflow before a specific event is not a convenient continuously monotonic guest clock. The programmable PMC0 tracks progress; the fixed counter carries the PEBS stop request. The VM-entry list stages values in an order that disables counters during reconfiguration and re-enables them after state is ready. This separation is visible in the PEBS module and the instruction counter.

Intel features Bedrock could use differently

EPT can be used for standard isolation, copy-on-write, dirty tracking, instruction guards or the PEBS record denial. Those uses have different performance profiles. An EPT mapping that stays valid can be very cheap after translation caching; a mapping intentionally set to fault on a hot path incurs repeated host transitions. VPID is valuable when frequent switches would otherwise discard translation state, but it cannot erase a stream of deliberate EPT violations. MSR bitmaps can avoid or request exits for selected register accesses. APIC virtualization can accelerate some guest interrupt-controller operations. Bedrock chooses controls around its replay model, so a feature's ordinary VM benchmark benefit does not automatically apply.

For the pinned Tempo test, we have a reported roughly 65-second Intel Bedrock run but not a matched Intel exit-count and cycle profile in this guide. We can explain precisely why the Intel design has a promising near-deadline stop, and we can compare the workload-family wall times with caveats. We cannot calculate how many of the AMD run's 42.8M exits would vanish on Intel from that one timing number. A fair experiment would pin guest kernel, image, seed and virtual duration, then capture the same exit categories and host timing on both architectures. [Comparison caveat]

Intel's VMCS selects exits for time reads, privileged operations, MSRs, I/O, EPT violations, external events and more. Bedrock uses VM-entry/exit MSR lists to swap its retired-instruction counter without counting host work. It programs IA32_PMC0 for guest INST_RETIRED.ANY_P, while a separate fixed counter feeds the precise stop. The code explicitly saves the counter on VM exit and reloads it on entry. [I1, B3]

For the stop, Bedrock arms PEBS on fixed counter 0. PEBS is normally a profiling feature: on a counter event, hardware writes a record to a buffer. AMD-V has the ingredients, but the stop arrives differently.

What AMD-V calls SVM

AMD's Secure Virtual Machine (SVM) extension gives a hypervisor control over when guest execution returns to it. The host prepares a virtual machine control block (VMCB), then executes VMRUN to enter the guest. The guest's ordinary arithmetic, loads, stores and branches execute on the physical core. When an intercepted instruction, event or nested-memory denial occurs, hardware saves guest state and returns to the host with an exit code and details. As on Intel, a guest kernel can run at its own CPL0 without gaining host authority. [AMD APM, Chapter 15]

The VMCB contains a control area and a state-save area. The control area defines intercepts, I/O and MSR permission maps, nested paging and event controls. The state area holds architectural guest state such as RIP and control registers. SVM checks these fields as it enters and exits. VMCB clean bits tell hardware that selected groups of control data have not changed since a prior entry, allowing it to avoid redundant reload work on supporting CPUs. This is a per-entry optimization, not a way to make a deliberately requested exit disappear. [AMD APM, VMCB and clean bits]

A useful way to read the VMCB is as memory with two jobs. Before VMRUN, the host writes policy and the guest's starting context. During guest execution, hardware consults that policy at instructions and memory accesses. On exit, hardware writes a reason and the saved guest context back for the host to inspect. Individual fields have distinct save and restore rules; the table is a conceptual reading guide rather than a byte-for-byte layout. [AMD APM, VMCB layout and transitions]

Nested paging is an independent permission layer

Nested Page Tables (NPT), also called rapid virtualization indexing (RVI), translate guest-physical addresses to host physical addresses. The guest still uses its own page tables to translate a virtual address to a guest-physical address. The CPU composes the two walks and can cache a final translation. If the guest tables deny an access, Linux receives #PF. If NPT denies it, the hypervisor receives a nested page fault (NPF). That distinction lets Bedrock make a page visible to Linux while intentionally stopping a selected write or fetch at the host boundary. [AMD APM, nested paging]

AMD uses an ASID to label guest translation state. The guest ASID lets cached translations survive some context transitions and prevents reuse under the wrong guest identity. The VMCB also has a TLB-control field for requesting flush behavior. When Bedrock changes NPT permissions, it must invalidate stale translations in the appropriate way before it relies on the new guard. ASID solves identity; invalidation solves freshness. Mixing those up can turn a proof of “this write must fault” into a false statement. [AMD APM, ASIDs and TLB control]

ROGPT: a small-sounding detail with a large measured effect

Bedrock's AMD planner protects not only code bytes but also the guest's page-table frames. If Linux rewrites a page-table entry, a previously checked virtual-to-physical alias may change; Bedrock therefore needs to learn about that write before trusting its execution plan. A natural strategy is to make those guest-table pages read-only in NPT. The snag is that ordinary hardware page walks can perform bookkeeping updates to the guest's accessed or dirty bits, and older behavior may request nested write permission during table walks more broadly. Without the right hardware support, read-only guards can provoke an NPF even on common translations that should have been fast.

Read-only guest page tables (ROGPT) changes this interaction: read-only walks need not be treated as nested writes except where an actual accessed/dirty-bit update is needed. On the tested 4245P, it makes a persistent guest-table guard practical. The same-box boot-and-fork ablation in this repo measured 18.49 seconds and 1.16M exits with ROGPT, versus 213.45 seconds and 122.55M exits without it. That result is for this guard design and workload; it is not a generic benchmark of all AMD-V systems. It shows how one small permission semantic can determine whether a hypervisor algorithm is viable. [AMD APM, ROGPT, Bedrock feature ablation]

Counting and notification are different jobs

AMD supplies performance-monitoring counters and an instruction-retired facility called IRPERF. On a CPU with the required PMC virtualization, host and guest PMU state can be separated across VMRUN transitions. Why a counter alone cannot run arbitrary code safely

Suppose the guest can retire an unbounded amount of work before Bedrock next regains control, or execute an instruction that changes what is being counted or observed. A safe fast path must bound where guest execution can go. The AMD backend decodes candidate code, marks unapproved code pages non-executable in NPT, protects code and relevant guest page tables from writes, and installs execution breakpoints at hazardous instructions that need special handling. If the guest fetches outside the approved region, hardware produces an NPF before that instruction executes. If the guest writes a protected page, the proof is invalidated before the write can silently change the code or mapping that was analyzed. [Bedrock AMD guarded-region planner]

A straight-line instruction block is easy to reason about: the decoder can count its instructions and identify its successor. An indirect branch, return, interrupt return, REP string operation or alias can make the path less predictable. Bedrock must either intercept the hazardous site, bound the possible successors, or use a narrower fallback. On x86 there are four address breakpoint slots, DR0 through DR3. AMD address masks can make one slot cover a range, but covering a hot innocent offset creates false exits. The planner therefore has a capacity problem as well as a correctness problem.

This is why “just batch more instructions” is not a safe optimization. If the code page can be modified, if a page-table write can remap a virtual alias, or if a branch can reach an unguarded hazardous instruction, the counted region may cease to describe the code actually executed. Bedrock's fast path repeatedly builds and validates these conditional proofs. The validation itself costs host cycles. When a workload frequently crosses approved page boundaries, asks for virtual time, or touches guarded tables, those exits and rebuilds become the dominant cost even though AMD-V can execute long uninterrupted regions quickly.

What an AMD feature does not automatically solve

IBS samples instruction behavior and is useful for profiling where time went. It is not established in this repo as a deterministic near-deadline stop like the Intel PEBS record-write trap. ASID helps translation reuse but cannot eliminate a deliberate NPF. VMCB clean bits can reduce entry-state work but cannot remove a clock-read intercept. TSC offset or scaling changes hardware time presentation, not an instruction-count clock. AVIC can reduce interrupt-controller overhead in suitable ordinary VMs, but Bedrock's exact event schedule still needs its own control path. Treating similar names as interchangeable obscures the measured bottleneck. [AMD APM, AMD IBS guide, Bedrock exit profile]

A concrete AMD run, from a code page to a clock boundary

Imagine the guest's RIP points into a Linux code page that Bedrock has not yet admitted to its fast region. The page is executable according to guest Linux, but NPT denies execute for that guest-physical frame. The CPU's instruction fetch therefore causes an NPF before the first instruction on that page begins. Bedrock reads the exit information, translates the guest address, examines code bytes, reasons about branches and hazardous instructions, and decides whether this page can join a bounded region. It protects relevant code and guest page-table frames against writes, assigns hardware execution breakpoints where needed, updates NPT permissions, invalidates stale translations, and enters the guest again at the same RIP. The reattempted fetch can now succeed. [Bedrock AMD planner]

While the approved region runs, ordinary guest loads, stores and branches flow through the physical core. IRPERF counts retired guest work. If the guest fetches a page outside the region, NPT brings Bedrock back before that instruction executes. If the guest writes code that was decoded for the proof, the read-only guard catches it before the bytes change. If Linux edits a protected page-table entry, the table guard catches the remap before an alias can silently redirect a supposedly safe virtual address. These are separate mechanisms enforcing the same invariant: the code Bedrock counted and bounded must be the code that actually executes.

Now the guest reads the clock. Bedrock intercepts RDTSC or RDTSCP and returns its emulated logical time. The current region ends; the next entry may need to reconstruct or validate parts of the plan. In the measured full run, roughly 14M clock-read exits make this a first-order cost, even if each individual clock handler seems small. It also explains why a plan-selection optimization can matter on exits that did not originate from a code fetch: every return to guest may need a safe entry plan. [Full-run exit profile, Virtual clock]

When a logical timer is due, the AMD backend arms a guest PMC overflow before the target, with a safety margin. The guest runs within the guarded region. On overflow, the CPU creates the virtual NMI delivery that Bedrock has arranged to trap through a temporary IDT limit. Bedrock restores the guest state, reads how far the guest actually retired, and finishes the exact boundary using a narrower method if needed. This is a different notification chain from Intel's PEBS record write, even though both use a retired-instruction count and a short final correction.

Why four breakpoint slots become a software architecture problem

An approved page is not necessarily a page whose every instruction is easy to count or safe to let run. The decoder may find REP strings, indirect control flow, interrupt returns or other operations that need special handling. An execution breakpoint can stop just before such an instruction. Four debug-address registers give four independently placed breakpoint slots. The AMD address-mask extension can make one slot cover a power-of-two-aligned range of offsets, but it may also catch non-hazardous instructions inside the range. Those are false hits: correct, yet expensive host returns.

Suppose a page has five hazardous offsets but only four slots. The planner could reject the page from the fast region, merge two hazards under one masked breakpoint, prove one hazard unreachable from current entry points, or use a slower fallback. Each choice has a different safety obligation. A mask must include every intended offset and can add hot false hits. A reachability proof must cover every possible branch, alias and code mutation under the current guards. A fallback increases exits. This is why a small-looking constraint in debug hardware becomes a large host-side planning cost.

The prior experiments in this branch make the tradeoff concrete. A breakpoint-mask trial reduced one capacity problem but caught hot normal code and regressed wall time. A multi-hazard feasibility probe found many pages where fewer slots might be possible, but making another page executable also requires a joint proof of all paths between pages. These are general hypervisor algorithm questions, not application-specific shortcuts. Yet the measured win has to be demonstrated on the full DST workload, because saving NPFs can still lose if each re-entry plan becomes more expensive. [Mask trial, Multi-hazard feasibility]

The guest page-table guard is easy to describe and difficult to implement efficiently. But the CPU itself walks these same guest tables constantly. On a CPU that requests nested write permission during an ordinary walk, every page translation can trip the barrier even though Linux did not intentionally edit a mapping. An EPYC 4244P and 4245P may look similar in product-family descriptions, but the Bedrock accelerated path depends on architectural bits exposed by the actual machine and host kernel. The safety envelope of a “fast” region

A region proof depends on a set of facts: code bytes have not changed, translations reach the frames analyzed, all possible outgoing fetches are stopped or admitted, hazardous instruction sites are trapped, the retirement counter is accurate, and a pending event cannot be passed unnoticed. Each fact needs a guard or a conservative fallback. The proof may be cached, but caching does not remove the need to check whether its dependencies are still true. On a hot path, revalidating the same facts after each clock exit can consume more cycles than the guest work between exits.

The engineering opportunity is therefore to make a broader region safe with fewer recurring validations, or to remove repeated exits such as clock reads with another deterministic time mechanism. The limit is correctness: an unnoticed write, virtual alias or late overflow can move a timer relative to instructions and invalidate replay. The performance section below treats measured exit categories separately so proposed changes can be assessed against the real ledger rather than a generic “AMD-V is slow” story.

AMD SVM uses VMRUN and a VMCB, with intercept bitmaps for instructions, MSRs and I/O. NPT provides the same broad second-stage role as EPT. AMD also has ASIDs for tagged translations and VMCB clean bits that can avoid reloading unchanged control groups. The Bedrock backend implements these foundations and shares much of its device, fork, randomness and exit-dispatch logic with Intel. [A1, B1]

On the tested EPYC 4245P, PMC virtualization swaps guest and host PMU state. Overflow raises a virtual NMI; Bedrock arranges for its delivery to fault at a temporary zero IDT limit before an interrupt frame is written, then restores the guest IDT controls and handles the stop. The implementation also intercepts SIDT/LIDT and IRET in counted regions so the temporary state cannot be observed or miscounted by ordinary guest execution. Why the AMD region has so many proof obligations

At a candidate entry, the planner reads the instruction window, checks whether the physical code page's bytes are still protected and validates the current CR3-dependent aliases. A simple straight-line block can often be decoded and assigned an exact static instruction count. A branchy block instead needs the hardware retirement count. For a global region, Bedrock selects a bounded set of pages, proves its code and translation tree stable, grants execute permission only to those pages, arms a counter period before the next logical deadline and installs up to four execution breakpoints at instructions that cannot run unchecked. A fetch from any other page causes an NPF before execution. [B4, B6]

Why four breakpoints? x86 exposes four address breakpoint registers, DR0–DR3. The AMD backend can use address masks to cover nearby offsets, but a mask may also hit normal hot instructions. Such a false hit requires host handling and can cost more than the fetch fault it avoided. Each physical page can have multiple executable virtual aliases, and a breakpoint address belongs to an alias, not to the physical page. If hazards and aliases cannot fit, the planner narrows the region or steps. If a guest write touches a guarded code or table page, Bedrock revokes the proof, replays the write safely and rebuilds. That is why a cached hazard scan is a conditional proof, not a permanent declaration that a page is harmless. [B4, B12]

ASID and VMCB clean bits can reduce translation and entry work, not remove a requested RDTSC intercept or a deliberately denied NPT fetch. Bedrock tested a clean-bit variant and saw no full-campaign improvement on the measured run. IBS is excellent for finding hot host instructions, but profiling a sample is not the same as stopping a guest exactly at instruction N. [I1, A1, B9]

Translate the concepts, then compare the control paths.

Intel and AMD both execute a Linux guest on the physical CPU, protect host memory through a second translation, and return to a hypervisor on selected events. Bedrock's timing path makes their less-obvious differences matter.

What is similar enough to reason about together?

Isolation: both architectures give the host an independent mapping from guest-physical pages to actual memory. A guest kernel changing its own CR3 does not let it escape that second stage. The host can deny an access and receive an exit. That is why Bedrock can use memory permissions as control signals on either architecture. Interception: both can return on selected instructions or events, so Bedrock can virtualize time and I/O. Direct execution: both can run long stretches of ordinary guest code on the physical core. These commonalities explain why a blanket claim that “AMD-V itself is millions of times slower” is wrong.

What does not translate one-for-one?

Near-deadline stop: Bedrock's Intel backend uses a PEBS record write denied by EPT. The tested AMD backend uses PMC virtualization, IRPERF, virtual NMI delivery and a temporary IDT limit. Both rely on counting and a precise finish, but their notification latency and host setup differ. Guest-table guard: ROGPT is a particularly important AMD feature for this backend's persistent NPT read-only protection. VMCB clean bits: AMD exposes this grouping hint; Intel has different VMCS handling and MSR-list facilities. These are architecture-specific details to test, not names to translate mechanically.

One implication is subtle. Intel's especially convenient PEBS/EPT stop can reduce the work needed to approach a deadline, but it does not tell us how much host work an equivalent Intel run spends on clock reads, page guards or devices. AMD's 42.8M exit ledger reveals a particular implementation and workload. To attribute a wall-time difference to hardware alone, we would need matched guests and similar profiling on both machines. The reported 65-second Intel run is an important product target, but it is not sufficient data to compute an intrinsic VT-x versus AMD-V multiplier. [AMD profile, Intel comparison caveat]

Where a conventional VM benchmark can mislead

A throughput VM may be dominated by memory bandwidth, I/O devices or a network stack. If it runs long uninterrupted intervals, entry/exit overhead is amortized and both hardware systems can appear nearly native. A deterministic test VM deliberately asks the host to own timing and event order. This can move the cost center to frequent exits, proof validation and precise stopping. A microbenchmark of one tight loop answers whether guest instructions run efficiently under a stable mapping. It does not answer whether Linux plus the Tempo DST test repeatedly crosses guarded code pages or reads virtual time. The Bedrock measurements show both behaviors on the same AMD feature-capable host.

Two hardware distinctions matter. First, counting and stopping are different capabilities: IRPERF can tell us how many instructions retired, but cannot alone force a timely exit. Second, a counter's interrupt is asynchronous with respect to the instruction whose count triggered it. The original Bedrock post measured hundreds of instructions of ordinary Intel PMI skid in one experiment; EPT-friendly PEBS removed the APIC delivery path. AMD's current backend instead uses the virtual-NMI/IDT technique plus bounded regions. A normal wall-clock VM timer is not equivalent to either. [P1, B6]

There are four distinct moments in a “counter interrupt”

First, the counter reaches its programmed value. Second, hardware decides that a notification is pending. Third, the notification is delivered through some architectural route. Fourth, Bedrock has executed enough host code to read the guest's actual progress and decide how to resume. Only the first is the counter event; only the last gives the hypervisor an opportunity to make a deterministic choice. Instructions can retire between them. That distance, often called skid, varies with the notification mechanism and with what the CPU was doing when the event became pending. A PMU that counts perfectly can therefore still be a poor exact-stop device.

Intel's PEBS/EPT construction changes the route between moments two and four. Rather than waiting for an ordinary performance-monitoring interrupt to traverse APIC delivery, PEBS hardware tries to store a record into a page whose EPT permission denies writes. The denied memory operation produces a VM exit close to the counter event. AMD's current path uses guest PMC overflow and virtual NMI delivery, then a temporary IDT-limit fault to regain control. IRPERF tells Bedrock how far the guest actually went. The early arm margin must leave enough room for that route's delay. The diagram's gap widths are illustrations; the required margin is an empirical and correctness-sensitive property of a supported host and path. [B5, B6]

What happens in the final few instructions?

After regaining control, Bedrock compares its observed retired count with the next logical event. If the target is near, it can use a precise but expensive step mechanism. On Intel, the monitor trap flag requests a VM exit after an instruction boundary; it is useful for finishing a short gap, disastrous if used for millions of instructions. The AMD backend similarly narrows execution to a fallback that can prove or observe the remaining work. This is why “make the skid zero” and “make every instruction cheap” are separate optimization questions. A near-stop reduces the length of the expensive finish. A guard planner reduces how often ordinary guest execution must stop at all.

Some x86 instructions complicate the word instruction. A REP MOVS encoding can copy many elements and be interrupted or resumed between iterations. A page fault can stop an attempted instruction before retirement. An interrupt may be pending while the guest is temporarily unable to accept it. HLT changes the relationship between guest work and perceived time because no instructions retire while the CPU is idle. A deterministic clock and exact deadline implementation must define what each of those cases means for its logical count and event ordering; programming a counter is only one part of that job.

The AMD acceleration is more than a PMU hookup. Bedrock scans code pages for instructions it must intercept before execution: controlled randomness, repeated strings, some privilege transitions and other hazards. It validates bytes and executable virtual aliases, then allows a bounded set of pages to execute through NPT. If a proof cannot cover a branch, store, alias or deadline, the runner falls back to narrower decoded blocks or single-step replay. [B4, B1]

Why a harmless-looking copy can become an exit storm

REP MOVS or REP STOS is one instruction encoding that performs many transfers. A string operation can be interrupted and restarted, and its destination can include code or a guest page table that Bedrock previously proved stable. Treating the whole operation as one ordinary retired instruction is insufficient for an exact deadline and unsafe for cached code proofs. Bedrock has a separate bounded native REP path: it validates the destination range, limits the chunk by the next deadline, accounts for iterations through RCX and invalidates cached code/table approvals that the copy could change. If that proof fails, execution narrows to the scalar path. This is a general mechanism, but a guest library that emits REP-heavy copies can still affect the workload's hazard-page mix. [B1, B4]

Control flow is the parallel problem. A direct branch has a statically visible target, so a bounded decoder can continue along both sides or place a stop at the outgoing target. A return or indirect jump can choose an address at runtime; it must be intercepted, bounded by another guard or proven to stay in a safe region. A page-local proof that begins at one RIP may be valid while every other page remains NX. If Bedrock also makes a second page executable, that second page can jump back into an offset the first proof never visited. The joint graph and the breakpoint placement must account for that return path before the pair is a safe optimization. [B4, B11]

That proof has to survive all guest paths, not just the hot path in a profile. A source page may jump into an alias, an interrupt can redirect control, a store can rewrite an instruction, a page-table change can remap the next fetch. The code therefore tracks guarded translation trees, mapping generations, cached hazard bytes and breakpoint capacity. A proof for one page is not automatically safe after a second page becomes executable: the second page may jump back into a previously unvisited hazardous offset. That is why the recent reachable-region diagnostics are capacity evidence rather than a merged execution shortcut. [B4, B11]

Guest shaping is real, but not the whole explanation.

Linux patches for randomness, delay loops, affinity reporting and some copy routines appear in this branch. Bedrock also intercepts CPUID: it presents a fixed Intel-like signature even on AMD to keep guest TSC calibration on the supported path, masks host-only or unsupported features, and hides ERMS from the AMD guest so optional copy dispatch tends away from REP. FSRM is hidden with the rest of leaf 7 EDX. Code that emits REP unconditionally will still do so. These choices support deterministic behavior or avoid troublesome guest instruction patterns. General hypervisor improvements—counter virtualization, ROGPT guards, native bounded execution, proof caches and successor planning—apply beyond one application. The pinned DST time still depends on the exact guest kernel and image; the reported Intel run used different hardware and guest assets. [B8, B19, B1]

Follow one run through the repository

The userspace runner asks /dev/bedrock for a VM, maps guest memory and prepares a Linux guest image. The kernel module sets up the CPU control structures and the nested mapping. Entering the guest does not “call Linux” as a Rust function: VMX or SVM loads a guest execution context, and the physical CPU begins fetching its instructions. The guest kernel boots, creates processes and handles their system calls in its own privilege domain. When hardware reports an exit, Bedrock's kernel-side handler sees the reason, updates emulated state or memory permissions, and resumes. The userspace runner remains responsible for campaign orchestration and requests that do not need to run on every exit. [B1]

For a clock read, the division of labor is concrete. A guest RDTSC reaches an intercept set in the virtualization controls. Hardware saves the necessary guest state and enters the host handler. Bedrock computes the virtual timestamp from logical progress, places the result where the guest instruction expects it, advances the guest instruction pointer as appropriate, and re-enters. For a normal guest system call, by contrast, user code enters guest Linux and later returns to user mode without a Bedrock exit unless some separate control fires. Confusing those two paths badly overestimates the unavoidable virtualization overhead.

Why the AMD planner lives above raw SVM

The Intel and AMD backends share the need to replay external inputs and to stop at an exact logical boundary. They differ in how they can safely let the guest run between boundaries. The AMD fast path builds a temporary claim: “within these approved pages, until one of these guarded events, execution can proceed without Bedrock missing an instruction or a state change that matters.” The claim depends on decoded code, virtual aliases, NPT permissions, protected guest page tables and available debug breakpoint slots. It can be invalidated by a code write, mapping edit or a branch outside the proved region. Each invalidation forces reconsideration before Bedrock runs freely again.

This is also where guest-shaping decisions enter. Bedrock controls some guest-visible features and supplies a patched guest kernel. Hiding a CPU feature can change which Linux or C-library routine gets chosen; patching a guest path can route randomness through a hypercall. Those are legitimate parts of a specific Bedrock deployment, but a speedup that depends on an image's instruction mix should be labeled as such. The guarded-region mechanism itself applies to arbitrary guest code when its proof succeeds. Its effectiveness is not constant across arbitrary programs: a tight arithmetic loop, a copy routine full of restartable string operations, and a kernel scheduler path create very different exit patterns.

20 / WHERE TIME GOES

Performance is an exit budget, not a GHz contest.

Where the seconds can come from

A performance claim about virtualization needs a workload and a denominator. “Five percent overhead” typically means a particular guest workload ran roughly 1.05 times its native wall time under particular conditions. “Two and a half times slower than Intel Bedrock” compares two hypervisor runs, not either run to native. “Millions of times slower than Valgrind” can describe an accidental single-step implementation on a microbenchmark without describing AMD-V hardware at all. These statements measure different things. This guide's relevant product question is the Tempo DST workload under Bedrock on Intel versus AMD.

For one run, a useful accounting identity is wall time = guest execution + entry/exit transitions + host handlers + setup and scheduling. These buckets are not trivially measured: a host profiler may count cycles in entry preparation, a guest counter counts retirements, and wall time includes descheduling and other system effects. Even “cost per exit” is an average across very different events. A clock read may have a small handler. A fetch NPF may trigger decoding, alias checks, breakpoint selection and NPT edits. A copy-on-write fault may allocate and copy a page. The same exit code can also be much cheaper when a cached proof is valid.

Why GHz is not the useful comparison

Processor frequency influences how quickly host and guest instructions execute, but it does not tell us how many VM exits the workload requests, how complex each plan is, or which feature gates are present. An EPYC core at a higher boost clock could lose to a lower-clocked host if it repeatedly exits or lacks a required PMU feature. An ordinary guest loop that stays in a stable region may run almost as quickly as native on that same EPYC. Bedrock's measured 38.659B-instruction memory loop on a 4245P did exactly that: 3.1625 seconds as a guest versus 3.1579 seconds native, with only thousands of exits. It is a useful hardware sanity check and a poor predictor of Linux DST time. [Microbenchmark record]

How to compare Intel and AMD responsibly

The ideal comparison pins the guest kernel, image, test seed, virtual duration, hypervisor revision and configuration while recording host CPU features, clock policy and exit statistics on each architecture. The Intel and AMD backends cannot be byte-for-byte identical internally, but the guest workload and observable success criteria can be. The current ~65-second Intel reference and ~161–166-second AMD pinned runs were obtained on different hosts and guest assets. They show an important practical gap for this workload family; they do not isolate hardware from software or guest-image effects. [AMD same-box A/B/A, Comparison caveat]

For performance engineering, the next question is narrower than “which vendor is faster?” It is: how many exits does a candidate change remove, which exit categories move, how much host work does it add to the remaining entries, and does the exact DST test still pass? This guide records the existing answer to the first part for AMD. It does not claim that one proposed optimization has already closed the Intel gap.

The useful first-order model is wall ≈ native guest work + Σ(exit count × exit cost) + host orchestration. The cost of an exit includes hardware transition, state save/restore, classification, proof construction, NPT edits, emulation and entry preparation. It is workload- and cache-dependent. Fewer exits can still lose if the new plan is much more expensive or creates false breakpoint hits. [B9, B12]

22 / THE GAP

Why does this workload still spend so much time in the host?

1

Clock reads are frequent and intentional.

About 14M exits are guest reads of virtual time. Passing the physical TSC through or merely offsetting it would be fast but would break Bedrock's instruction-count clock. An alternative needs to preserve replay and exact timer semantics. One AMD guest PMC-clock experiment cut clock exits in a short run but did not establish a full-run win or a general replacement. [B2, B15]

2

Guarded code transitions fault constantly.

About half of the exits are NPT faults. Bedrock admits only code pages whose instructions, aliases, writes and outgoing paths it can guard under its four hardware breakpoint slots. Hot Linux scheduler and userspace pages are revisited as execution moves across code. A sampled fetch-fault analysis found 45.1% of candidate faults appeared to exceed the four-slot breakpoint budget with the existing page proofs; others fell outside the selected recent-page set. This identifies a software proof/capacity problem, not a slow page-table walk alone. [B16, B9]

3

Every return to the host prepares another safe entry.

The profiled entry-preparation path consumed 37.1% of recorded cycles. It chooses a plan, checks translations, code and table guards, selects pages, installs permissions and breakpoints, updates PMU/VMCB state, then resumes. A local phase probe assigned much of clock-exit preparation to plan selection. Some caching trials passed correctness tests but bought little full-run time because validation and invalidation still cost work. [B9, B1]

4

Exactness narrows legal shortcuts.

REP strings, indirect branches, IRET, aliases, self-modifying code, COW remaps and guest page-table writes can invalidate a naive multi-page proof. Synthetic MTF still accounts for 5.5M exits. Intel's PEBS stop reduces a different cost: how closely the CPU can exit near a target. It does not automatically solve AMD's page-guard planner, and AMD's IRPERF does not automatically give Intel's PEBS trap. [B4, B5]

So the accurate answer is both hardware affordance and implementation design. AMD has efficient SVM/NPT and can run long regions near native speed on the 4245P. Bedrock's Intel path has an especially convenient near-exact PEBS/EPT stop. The AMD path compensates with complex bounded execution; on this Linux DST workload, that causes many NPT, clock and fallback exits. The 4244P case adds a hard feature gate—no PMC virtualization in the observed allocation—but that is not the host used for the ~165s run.

Turn the exit counts into a cost model

A rough wall-time model is native guest work + exits × average exit cost + host planning + device and campaign work. It is not an identity you can fill with one universal “VM exit cost”: a clock read, NPT fetch fault, page-table write and exact-step exit take different handler paths. But the model forces useful questions. If a run has about 14 million clock exits, shaving a few cycles from one rare VMCB field update cannot remove most of those returns. If it has about 21.8 million NPFs, a faster instruction counter alone cannot erase the repeated guard transitions. And if entry preparation consumes a large fraction of recorded cycles, a seemingly small software plan-selection improvement can matter even without new silicon. [B9]

Those terms interact. Combining two guarded pages could reduce NPFs but require more breakpoints. Masking two nearby hazards into one breakpoint slot could cover a hot harmless instruction and create false hits. Caching an approved region could avoid repeated decoding but make validation or invalidation more expensive. A software change should be evaluated by the entire campaign's wall time and correctness, not just by the count it was designed to lower. The same-box A/B/A result later in this guide is evidence for a particular planner change on a particular pinned workload; it is not evidence that every source of overhead was solved.

What would close the gap?

There are plausible routes, but they have different proof burdens. A guest-visible clock path that avoids a host exit for common reads would attack the largest exit class, provided it preserves the instruction-count semantics. More reusable guarded regions or better hazard placement could reduce NPT transitions, provided every reachable code path and remap remains covered. Cheaper entry-plan selection could reduce host work per remaining exit. Better use of CPU-specific PMU and translation features could improve particular hosts. None of these can be assumed from the feature name alone; each needs a correctness test and a same-workload timing test against the current implementation.

The strongest positive evidence is that an AMD 4245P can already run a long, guarded guest memory loop close to native speed. The strongest negative evidence is the Linux DST campaign's millions of purposeful exits and the roughly 161–166-second AMD wall time against the reported ~65-second Intel reference. Together they say that the core is capable of fast guest execution, while this workload's control-plane path is still expensive. They do not prove a hard architectural floor at the current number, nor do they establish that a one-week effort will reach the Intel result. [B1, B9]

23 / CAN IT CLOSE?

Probably improvable. Seventy seconds in a week is not a forecast.

Moving from ~165s to ~70s requires about a 2.36× end-to-end speedup and removing roughly 95 host seconds. Our best validated recent planner change saved ~8–12s on a same-box seed. Some technically plausible trials passed the workload but did not improve wall time, including broader breakpoint masks, root reproof and VMCB clean-bit changes. This history makes ~70s a stretch requiring a major, measured reduction in exits or per-exit work, not another small local optimization. [B13, B9, B12]

The most promising general directions are proofs that safely keep more hot code executable without false breakpoint hits; fewer repeated guest-table/code guards; and a virtual-clock mechanism that removes RDTSC exits while preserving instruction-count time. A two-to-four-hazard single-page feasibility probe found smaller breakpoint sets in 14,206 of 20,480 sampled current-page plans, but making a second page executable requires a joint proof of paths back into the first page. That capacity result is not a wall-time result. IBS and hypothetical PEBS-like AMD record-write tricks are also unproven as deterministic deadline primitives here. [B11, A2]

A reliable Intel comparison would run the same pinned workload, seed, guest kernel and container image on documented Intel and AMD hosts, record CPU features and frequency behavior, and collect exit counts and host cycles from both. Until then, we can say the AMD branch works on the pinned test and is roughly 2.5× slower in the available cross-machine reference, but we cannot attribute that ratio solely to VT-x versus AMD-V. The architecture itself does not impose a known 2.5× tax. The measured exit mix gives concrete software work to reduce. [B13, B9]

The ordinary machine

Instruction

An architectural operation encoded in program bytes. A core may implement it with several internal operations. Guest instructions normally execute on the actual CPU under virtualization.

RIP

The x86-64 instruction pointer: the architectural address of the next guest or host instruction. A VM exit reports guest RIP so the hypervisor can decide whether to retry or advance.

General-purpose register

Architecturally visible storage such as RAX and RBX used for operands, addresses and results. These are different from control registers and PMU configuration MSRs.

Retirement

The point at which an instruction's result becomes part of the architectural execution stream. Speculatively executed instructions that are discarded do not retire.

Cycle

A unit of core clock progress, not a synonym for a retired instruction. Memory stalls, branch recovery and host work can use cycles without advancing the guest instruction count.

CPL

Current privilege level. CPL3 is typical application execution; CPL0 is kernel execution. VMX/SVM guest status is a separate axis from CPL.

Control register

A privileged architectural register controlling machine state. CR3 selects a page-table root; other CR registers control paging and execution modes.

MSR

Model-specific register. A vendor-defined control or status register accessed with privileged instructions. PMU events, PEBS controls and other virtualization-relevant facilities use MSRs.

CPUID

An instruction through which software discovers processor capabilities. A hypervisor can intercept and present a virtual feature set, as Bedrock does for its guest.

Out-of-order execution

Internal scheduling of ready work before earlier stalled work completes. The CPU still retires architectural results in a valid order. It helps explain why instruction count and elapsed cycles diverge.

Speculation

Work performed before the CPU knows it is on the correct path, such as after a branch prediction. Discarded speculation consumes resources but does not advance retired-instruction count.

Memory and protection

Virtual address

The address a process or guest program uses. Its interpretation depends on the active page-table root; the same number can name different physical frames in different processes.

Physical frame

A page-sized region in physical memory. A guest physical frame is an address in the VM's invented physical address space; a host physical frame is real machine memory.

Page table

A hierarchy mapping virtual pages to physical frames and carrying permissions. Guest Linux manages its own tables, while EPT or NPT supplies a separate host-owned mapping.

CR3

The x86-64 control register naming the current guest or host page-table root. Changing CR3 can change what a virtual pointer means.

Page walk

Hardware following page-table entries to translate an address. A TLB hit can bypass most of this work. Under virtualization, guest and nested walks compose.

TLB

Translation lookaside buffer: a cache of address translations. It accelerates repeated memory access but requires correct invalidation after mapping or permission changes.

Guest page fault (#PF)

A guest page-table failure handled by guest Linux, unless the hypervisor specifically intercepts that event. It is not the same as an EPT violation or AMD nested-page fault.

EPT

Intel Extended Page Tables, the host-controlled second translation from guest physical to host physical memory. EPT can deny read, write or execute and report violations to the VMM.

NPT / RVI

AMD Nested Page Tables / rapid virtualization indexing. NPT serves the same broad second-stage mapping role as Intel EPT, though controls and detailed semantics differ.

NPF

AMD nested page fault: a second-stage memory denial returned to the host. Bedrock uses NPFs as guards around code, guest page tables and out-of-region fetches.

NX

Non-executable permission. If a required execute permission is absent, the CPU cannot fetch that instruction from the page. Bedrock uses nested NX to bound approved code regions.

Alias

A second virtual address reaching the same guest-physical page. A physical-page guard and a linear-address breakpoint have different coverage; proof logic must account for both aliases.

VPID / ASID

Intel and AMD mechanisms for tagging guest translation contexts. They can retain TLB entries across transitions, but a changed mapping still needs appropriate invalidation.

ROGPT

AMD read-only guest page-table support. It makes Bedrock's NPT read-only protection of guest table frames compatible with ordinary page walks on supported CPUs, avoiding a large class of false NPFs.

Virtualization control

VMM / hypervisor

Host software that configures and handles virtual execution. In this guide Bedrock is the VMM, and Linux plus applications run as its guest.

VM entry

A processor transition from host control into guest execution after the host has configured guest state and controls. Entry has hardware and host-preparation costs.

VM exit

A transition from guest execution back to the VMM due to an intercept, event or nested-memory violation. The host examines the reason and determines how to resume.

VMCS

Intel VM-control structure. It holds VMX control choices, guest and host state, and VM-exit information according to the SDM's field-specific rules.

VMCB

AMD virtual machine control block. Its control and state areas govern SVM guest execution and record exit information.

VMX root / non-root

Intel's host and guest execution modes. A non-root guest kernel can still be CPL0 within its VM.

SVM / VMRUN

AMD Secure Virtual Machine architecture and the instruction used to enter a guest according to a VMCB.

Intercept

A configured operation or event that causes control to return from guest to host. Clock reads, selected MSRs and I/O are examples.

Exit qualification

Extra information accompanying a VM-exit reason, such as the type of EPT access that failed. The VMM uses it to choose the right handler.

MSR list

Intel's VM-entry/exit facility for loading or storing selected MSR values as part of transitions. Bedrock uses it to keep guest PMU count separate from host work.

VMCB clean bits

AMD hints that groups of VMCB fields have not changed, allowing hardware to avoid some reload work. They reduce possible entry overhead, not exit count.

Copy-on-write

A memory strategy that shares unchanged pages between related VM states and copies a page when it is written. Bedrock uses it for replay forks.

Deterministic time and measurement

TSC

Time stamp counter, read by RDTSC/RDTSCP. Raw host TSC tracks hardware time, so Bedrock intercepts reads and returns a virtual instruction-count-based value.

PMU / PMC

Performance monitoring unit and counter. Hardware can count events such as retired instructions; a counter alone does not guarantee an exact software stop at the count.

IRPERF

AMD instruction-retired performance counter facility. Bedrock uses it to account for how many guest instructions actually retired in a bounded region.

PEBS

Intel Precise Event-Based Sampling. On supported CPUs, Bedrock deliberately denies a PEBS record write through EPT to regain control near a logical deadline.

IBS

AMD Instruction-Based Sampling. A useful profiling source, but not established in this repo as an exact deadline-stop replacement for the Intel PEBS/EPT interaction.

Skid

Extra guest instructions that retire between a counter event and observable notification. Variable skid is why an ordinary PMU interrupt is not enough for exact replay timing.

MTF / single-step

Monitor trap flag on Intel, or a comparable stepping fallback, returns control after a very small amount of guest progress. It is useful for the exact final interval and expensive as a continuous loop.

Virtual NMI

An AMD SVM mechanism for a non-maskable-interrupt-like notification in guest context. Bedrock uses it as part of its counter-overflow stop path.

IDT

Interrupt descriptor table, which selects exception and interrupt handlers. The AMD backend temporarily constrains guest IDT delivery to convert a virtual NMI into a host-observable stop.

Breakpoint register

One of the x86 DR0–DR3 address breakpoint slots. Bedrock's AMD planner uses them to stop before hazardous instruction sites in an approved executable region.

Guarded region

A set of guest code pages Bedrock has analyzed and allowed to execute under NPT code, table and breakpoint guards. Leaving the region returns to the host before unapproved code runs.

Logical deadline

A guest instruction-count boundary at which Bedrock must expose a scheduled timer or event. It is not a number of host nanoseconds or CPU cycles.
