What has to be the same in a replay?

Imagine two workers that race to acquire one lock. Repeating their program bytes is not enough to repeat the winner. The relative order of their runnable periods, a timer interrupt, an incoming packet, or a returned random value can change the state at which either worker attempts the lock. A deterministic system therefore needs a rule for when each external influence becomes visible. In Bedrock, the central coordinate is the number of guest instructions retired. If an event was delivered at guest count N in the first execution, replay must arrange delivery at the equivalent logical boundary, even if host wall time or cache warmth differs.

The count is a coordinate, not a complete replay log. The initial RAM image, CPU state, disk and device contents, number of virtual CPUs, guest-visible feature set, and all injected inputs also matter. If one fork starts with a different page-table entry or a different CPUID result, both may retire the same number of instructions while reaching unrelated states. Bedrock's copy-on-write fork gives variants a common starting snapshot. Its device and randomness boundaries turn external observations into controlled values. A test campaign can then vary a schedule or input deliberately and know which change it introduced. [B7, B8]

Why a time read is an input, even though no one sent a packet

Consider an application that calls clock_gettime, checks whether a retry deadline has passed and chooses a branch. If the returned time depends on the host's current clock, a cache miss or a host preemption can change that branch on replay. The application can observe that difference even when the guest's memory and instruction stream were initially identical. Bedrock therefore controls the guest-visible clock, including direct RDTSC and RDTSCP reads where they are intercepted. Its logical clock is derived from retired guest work, with explicit treatment for time spent idle. A Linux system call that reads a clock is still a guest-kernel operation; it only becomes deterministic if the clock source that kernel consults is controlled too. [B2]

A boundary must also be precise. Suppose a timer is due after instruction 100,000, and a worker releases the lock at instruction 100,002. Delivering the timer at 99,998 and 100,003 produces different legal schedules. “A counter eventually interrupted us” does not guarantee the same ordering. This is why the vendor sections spend so much space on the hardware route from a counter event to an actual host stop. The exactness requirement is imposed by replay semantics; the PMU and virtualization features are tools for meeting it.

What deterministic execution does not promise

A deterministic schedule does not make a buggy program correct, nor does it imply that every possible schedule has been explored. It makes an execution reproducible under the controlled inputs and CPU model. DST uses that property to explore chosen alternatives and replay a failure. It also means a performance result must be interpreted carefully: a 180-virtual-second campaign can finish in less or more than 180 host seconds because virtual time and host time represent different things. The user-facing comparison later in this guide is between equivalent Bedrock campaigns, with their guest assets and host hardware called out, rather than a ratio between a virtual duration and a wall-clock stopwatch.
