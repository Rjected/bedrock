SYSTEM / DETERMINISTIC TESTING

What does a DST hypervisor give an application?

The application is still a normal guest program using Linux services. The deterministic test system controls what the program can observe from outside its own execution.

Picture a service test that starts several processes, opens sockets, reads the clock, asks for random bytes and waits on timers. Native execution lets the host OS and real hardware choose many observation points. A deterministic test instead needs a controlled schedule and input stream, so a failing run can be reproduced from the same initial state and choices. Bedrock supplies a Linux guest, virtualized devices, a logical clock and forkable memory state. The guest is not a binary translator: application and kernel instructions usually run on the physical CPU. The hypervisor intervenes at selected boundaries to make the outside world controlled.

Time is an especially invasive input. A program may read it directly or through a library. Linux itself calibrates and uses timers, so the guest must see a coherent clock. Bedrock intercepts CPU time reads and computes virtual TSC from retired guest instructions plus controlled idle offset. A timer delivery is then tied to a logical count, not “however many instructions happened to run before the host woke up.” The Intel and AMD paths differ in how they get the CPU to stop near that count, but the guest-facing goal is the same.

Randomness must also be controlled. Bedrock's guest patch routes kernel randomness through a hypercall, making bytes an explicit input to the deterministic system. A service using a random API does not need to know which CPU instruction or kernel source produced the bytes; it needs the test to return a controlled sequence. The hypervisor must be careful not to mistake “fixed seed” for a complete solution: scheduling and device delivery can still create different execution if they are not controlled. [Guest patches]

Virtual devices and I/O define another observation boundary. The application issues ordinary syscalls; the guest kernel's drivers interact with the virtual machine. Bedrock can decide what data arrives and when an event becomes visible. The details of any particular virtual device are outside this CPU-focused guide, but the architectural point matters: a CPU counter alone would not make network or disk responses reproducible. A DST system composes a precise execution coordinate with controlled inputs and event delivery.

Forking lets a test explore another schedule or input from a related VM state. Bedrock uses copy-on-write memory so a child can share unchanged pages with a parent and pay for copies only on writes. Deterministic execution then gives those branches meaningful, reproducible starting points. A guest write may therefore trigger a memory-management exit for copy-on-write independent of AMD's executable-region planning. When profiling VM exits, it matters which subsystem asked for the stop. Where the application actually spends time

If the service performs CPU work or memory access inside a stable approved region, hardware executes it directly, so that interval can be fast. If it calls the clock frequently, crosses many code pages, performs many device operations or triggers copy-on-write writes, the hypervisor runs more often. The slowdown is the sum of those interactions, not a fixed tax on every Rust instruction. The long memory-loop result on AMD and the full DST exit profile illustrate the extremes: one has few host returns over billions of instructions; the other has tens of millions of returns over the campaign.

This is why the exact guest kernel and image matter for a fair Intel/AMD test. Linux copy routines, TSC calibration, page layout and application libraries determine which instructions execute and how frequently they cross Bedrock's guard boundaries. Bedrock can shape some guest behavior through CPUID and patches, but a benchmark on one guest image cannot be attributed entirely to the host CPU. The clean performance question is still practical: with the workload Tempo actually cares about and an equivalent guest, how quickly do the two Bedrock backends complete and pass the deterministic test?
