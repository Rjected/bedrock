COMPARISON / SAME JOB, DIFFERENT PRIMITIVES

Translate the concepts, then compare the control paths.

Intel and AMD both execute a Linux guest on the physical CPU, protect host memory through a second translation, and return to a hypervisor on selected events. Bedrock's timing path makes their less-obvious differences matter.

For an ordinary integer add or permitted memory load, neither vendor requires per-instruction host software. VMX and SVM are both hardware virtualization systems. Intel's VMCS and AMD's VMCB are different control formats with different entry instructions and detailed semantics, yet each configures guest state, intercepts and nested paging. EPT and NPT play similar broad roles as host-owned second-stage mappings. VPID and ASID play similar broad roles as translation-context tags. Similar role does not mean identical feature bits, invalidation rules or behavior for a particular counter event. The feature that matters most to this Bedrock comparison is the way a count becomes a near-exact host return. [Intel SDM, AMD APM]

What is similar enough to reason about together?

Isolation: both architectures give the host an independent mapping from guest-physical pages to actual memory. A guest kernel changing its own CR3 does not let it escape that second stage. The host can deny an access and receive an exit. That is why Bedrock can use memory permissions as control signals on either architecture. Interception: both can return on selected instructions or events, so Bedrock can virtualize time and I/O. Direct execution: both can run long stretches of ordinary guest code on the physical core. These commonalities explain why a blanket claim that “AMD-V itself is millions of times slower” is wrong.

What does not translate one-for-one?

Near-deadline stop: Bedrock's Intel backend uses a PEBS record write denied by EPT. The tested AMD backend uses PMC virtualization, IRPERF, virtual NMI delivery and a temporary IDT limit. Both rely on counting and a precise finish, but their notification latency and host setup differ. Guest-table guard: ROGPT is a particularly important AMD feature for this backend's persistent NPT read-only protection. VMCB clean bits: AMD exposes this grouping hint; Intel has different VMCS handling and MSR-list facilities. These are architecture-specific details to test, not names to translate mechanically.

One implication is subtle. Intel's especially convenient PEBS/EPT stop can reduce the work needed to approach a deadline, but it does not tell us how much host work an equivalent Intel run spends on clock reads, page guards or devices. AMD's 42.8M exit ledger reveals a particular implementation and workload. To attribute a wall-time difference to hardware alone, we would need matched guests and similar profiling on both machines. The reported 65-second Intel run is an important product target, but it is not sufficient data to compute an intrinsic VT-x versus AMD-V multiplier. [AMD profile, Intel comparison caveat]

Where a conventional VM benchmark can mislead

A throughput VM may be dominated by memory bandwidth, I/O devices or a network stack. If it runs long uninterrupted intervals, entry/exit overhead is amortized and both hardware systems can appear nearly native. A deterministic test VM deliberately asks the host to own timing and event order. This can move the cost center to frequent exits, proof validation and precise stopping. A microbenchmark of one tight loop answers whether guest instructions run efficiently under a stable mapping. It does not answer whether Linux plus the Tempo DST test repeatedly crosses guarded code pages or reads virtual time. The Bedrock measurements show both behaviors on the same AMD feature-capable host.
