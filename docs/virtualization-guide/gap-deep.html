Turn the exit counts into a cost model

A rough wall-time model is native guest work + exits × average exit cost + host planning + device and campaign work. It is not an identity you can fill with one universal “VM exit cost”: a clock read, NPT fetch fault, page-table write and exact-step exit take different handler paths. But the model forces useful questions. If a run has about 14 million clock exits, shaving a few cycles from one rare VMCB field update cannot remove most of those returns. If it has about 21.8 million NPFs, a faster instruction counter alone cannot erase the repeated guard transitions. And if entry preparation consumes a large fraction of recorded cycles, a seemingly small software plan-selection improvement can matter even without new silicon. [B9]

Those terms interact. Combining two guarded pages could reduce NPFs but require more breakpoints. Masking two nearby hazards into one breakpoint slot could cover a hot harmless instruction and create false hits. Caching an approved region could avoid repeated decoding but make validation or invalidation more expensive. A software change should be evaluated by the entire campaign's wall time and correctness, not just by the count it was designed to lower. The same-box A/B/A result later in this guide is evidence for a particular planner change on a particular pinned workload; it is not evidence that every source of overhead was solved.

What would close the gap?

There are plausible routes, but they have different proof burdens. A guest-visible clock path that avoids a host exit for common reads would attack the largest exit class, provided it preserves the instruction-count semantics. More reusable guarded regions or better hazard placement could reduce NPT transitions, provided every reachable code path and remap remains covered. Cheaper entry-plan selection could reduce host work per remaining exit. Better use of CPU-specific PMU and translation features could improve particular hosts. None of these can be assumed from the feature name alone; each needs a correctness test and a same-workload timing test against the current implementation.

The strongest positive evidence is that an AMD 4245P can already run a long, guarded guest memory loop close to native speed. The strongest negative evidence is the Linux DST campaign's millions of purposeful exits and the roughly 161–166-second AMD wall time against the reported ~65-second Intel reference. Together they say that the core is capable of fast guest execution, while this workload's control-plane path is still expensive. They do not prove a hard architectural floor at the current number, nor do they establish that a one-week effort will reach the Intel result. [B1, B9]
