Follow one run through the repository

The userspace runner asks /dev/bedrock for a VM, maps guest memory and prepares a Linux guest image. The kernel module sets up the CPU control structures and the nested mapping. Entering the guest does not “call Linux” as a Rust function: VMX or SVM loads a guest execution context, and the physical CPU begins fetching its instructions. The guest kernel boots, creates processes and handles their system calls in its own privilege domain. When hardware reports an exit, Bedrock's kernel-side handler sees the reason, updates emulated state or memory permissions, and resumes. The userspace runner remains responsible for campaign orchestration and requests that do not need to run on every exit. [B1]

For a clock read, the division of labor is concrete. A guest RDTSC reaches an intercept set in the virtualization controls. Hardware saves the necessary guest state and enters the host handler. Bedrock computes the virtual timestamp from logical progress, places the result where the guest instruction expects it, advances the guest instruction pointer as appropriate, and re-enters. For a normal guest system call, by contrast, user code enters guest Linux and later returns to user mode without a Bedrock exit unless some separate control fires. Confusing those two paths badly overestimates the unavoidable virtualization overhead.

Why the AMD planner lives above raw SVM

The Intel and AMD backends share the need to replay external inputs and to stop at an exact logical boundary. They differ in how they can safely let the guest run between boundaries. The AMD fast path builds a temporary claim: “within these approved pages, until one of these guarded events, execution can proceed without Bedrock missing an instruction or a state change that matters.” The claim depends on decoded code, virtual aliases, NPT permissions, protected guest page tables and available debug breakpoint slots. It can be invalidated by a code write, mapping edit or a branch outside the proved region. Each invalidation forces reconsideration before Bedrock runs freely again.

This is also where guest-shaping decisions enter. Bedrock controls some guest-visible features and supplies a patched guest kernel. Hiding a CPU feature can change which Linux or C-library routine gets chosen; patching a guest path can route randomness through a hypercall. Those are legitimate parts of a specific Bedrock deployment, but a speedup that depends on an image's instruction mix should be labeled as such. The guarded-region mechanism itself applies to arbitrary guest code when its proof succeeds. Its effectiveness is not constant across arbitrary programs: a tight arithmetic loop, a copy routine full of restartable string operations, and a kernel scheduler path create very different exit patterns.
