BRIDGE / DETERMINISTIC REPLAY

Why stop at instruction 100,000 instead of “about now”?

A deterministic test controls the order in which the guest sees time, interrupts and outside input. Delivering the right event a few instructions late may produce a different execution.

Imagine a guest thread holding a lock. A timer should arrive just before the instruction that releases it. If the timer instead arrives just after the release, the scheduler may run a different thread first. The final state might coincidentally match in a simple test, but the execution history and race exposure have changed. Bedrock therefore needs a logical coordinate for events. It uses retired guest instructions as the principal execution clock, then emulates time reads and manages idle offsets so guest-visible time is derived from controlled state rather than from host frequency or scheduling delays.

Determinism requires more than a counter. External inputs, device responses, random bytes, interrupts, process forks and time reads all need controlled behavior. Bedrock uses hypervisor exits to own those boundaries. It also patches its Linux guest to route certain randomness through a hypercall and to shape behaviors that would otherwise introduce untracked or awkward nondeterminism. These guest changes are part of the system design, not evidence that AMD hardware cannot virtualize an unmodified application. [Bedrock guest patches, Bedrock virtual time]

There are several tempting shortcuts that fail this contract. Passing through the host TSC is fast, but the host clock advances during descheduling and can differ between runs. TSC offset and scaling alter the number a guest sees but still tie it to physical time. A regular wall-clock timer can interrupt after the guest retires a variable number of instructions. A PMU overflow tells Bedrock that a count was reached, but software notification may arrive after more instructions retire. Each shortcut may be acceptable for an ordinary VM and unsuitable for a deterministic replay boundary.

Once a near-exact stop is available, Bedrock can let large regions run directly on the CPU and regain control only when necessary. That is the performance ambition shared by the Intel and AMD backends. Their difficulty is not “can the core execute guest code?” Both can. The difficult question is “can we bound what runs, know how many guest instructions retired, and regain control soon enough to inject the next event at exactly the right point?”
