Begin with one instruction, not a virtual machine.

A CPU repeatedly finds an instruction, works out what it means, performs its work, and makes its result part of the program's visible state. Hardware virtualization does not replace that engine. It changes the conditions under which the engine is allowed to keep going.

Suppose a Rust program eventually executes the x86-64 instruction mov rax, [rbx]. The architectural story is short: read the address in rbx, load eight bytes from memory, put them in rax, and advance to the next instruction. The machine may actually fetch ahead, decode several instructions, execute work out of order, and consult multiple caches. Software normally sees the retired result: the point at which an instruction becomes architecturally committed. An instruction that was speculatively executed and then discarded did not retire.

RIP is the x86-64 instruction pointer: it names the instruction the architectural machine will execute next. RAX and RBX are general-purpose registers, fast named storage locations visible to software. An instruction can use register values without touching memory, or it can use a register as an address as our load does. A VM exit later reports a guest RIP so the hypervisor knows where guest execution stopped; that statement only makes sense once RIP has a concrete meaning.

“One instruction” does not mean “one clock cycle.” A cached addition may complete quickly; a cache miss may wait hundreds of cycles. A single REP string instruction can perform many element copies and may be interrupted and resumed partway through. Bedrock therefore cares about the exact architectural event it counts, while real elapsed time still depends on caches, memory and scheduling. The distinction between retired instructions and cycles is the basis of the whole performance story.

What a Rust pointer becomes on this machine

A Rust expression such as let x = *ptr; does not inherently mean one CPU instruction. The compiler chooses instructions based on type, optimization level, surrounding code and target features. For a simple 64-bit load, the machine may eventually execute a form like mov rax, [rbx]. The address in RBX is still a virtual address until paging hardware translates it. RAX is a destination register. If the access is permitted, the loaded value becomes visible when the instruction retires. If the mapping is missing, the CPU raises a fault and the load does not retire as a completed load.

This separation between an instruction's architectural meaning and its physical implementation will recur. Architecturally, an x86 load reads memory and changes a register. Internally, the core may look up a translation, search caches, speculate past a branch, wait for memory, or replay internal work. Hardware virtualization adds permission and intercept checks to this machinery. It does not require Bedrock to receive a callback for each successful ordinary load. Bedrock gets control only at events it configured, faults in the host-owned memory layer, or other architecturally defined exits.

One more x86 wrinkle matters later: the word “instruction” does not always imply a small fixed amount of work. A REP-prefixed string operation can copy many elements while retaining a single program-level instruction identity. Some instructions can be interrupted and resumed partway through their work. A safe deterministic execution plan must know what its counting and stop mechanisms mean around such instructions. This is one reason the AMD planner classifies REP sites as hazards instead of assuming every decoded instruction is a trivial one-step unit.

FOUNDATION / 02

What state makes an instruction mean something?

The same instruction bytes can behave differently depending on the current register values, address space and privilege level. That context is CPU state.

General-purpose registers hold operands and results. RIP selects the next instruction. RFLAGS holds condition and control flags. Other registers have system-level jobs: CR3 points at the current top-level page table; other control registers enable paging and other processor modes. Software also uses model-specific registers, or MSRs, to configure hardware features such as performance counters. MSRs are not a bag of normal program variables: many require privileged instructions to read or write, and their meanings are defined by the CPU vendor.

Privilege adds a second axis. Application code normally runs with less authority than the operating-system kernel. On x86, CPL is the current privilege level; CPL3 is typical application code and CPL0 is the kernel. A normal application cannot rewrite CR3 or configure hardware counters at will. A system call deliberately switches from application code into the kernel. A page fault or interrupt also transfers control, but for different reasons.

Virtualization adds another axis, separate from CPL. Intel calls the hypervisor's mode VMX root and the guest's mode VMX non-root. A Linux guest kernel can be at its own CPL0 while still in non-root mode. AMD has an analogous host/guest split under SVM. The guest kernel has enough authority to manage its virtual machine, but the hypervisor retains control of actual memory ownership and selected hardware events. This is why “guest root” is not “host root.”

We will later see VMCS on Intel and VMCB on AMD. They are records holding guest state and control choices. Before seeing either, keep the simpler picture: entry loads a coherent context; exit gives the host a reason to inspect or change that context. [Intel SDM, AMD APM]

Which state belongs to a process, a guest, or the host?

In an ordinary process switch, Linux saves enough application registers to resume that process later and changes the active address space. A virtual-machine switch is broader: the CPU moves between host and guest execution modes and may also move selected control state. Some guest state lives in VMCS/VMCB fields; some is held in processor registers while the guest runs; some is saved or restored by host code. The architectural manual defines the exact division. A hypervisor cannot treat a VMCS or VMCB as a plain Rust struct whose fields automatically mirror every physical register at all times.

CR3 is particularly important because it changes the meaning of nearly every virtual address. If Bedrock approves code under one guest CR3 and the guest switches address spaces, the same RIP value might translate to different bytes. The AMD guarded-region planner therefore reasons about translation dependencies, not merely instruction addresses. By contrast, a general-purpose register such as RAX often holds a temporary result that changes many times per function call; it does not define a global address-space mapping.

MSRs control hardware facilities rather than ordinary computation. A PMU event-selection MSR can choose “instructions retired,” a counter MSR can hold the numeric count, and virtualization MSRs can configure entry or control features. The host must decide what the guest is allowed to read, write or observe. Intel's Bedrock path uses VM-entry and VM-exit MSR lists to move PMU state; the tested AMD path uses PMC virtualization. The goal is the same: guest count should reflect guest progress, while Bedrock's host instructions remain outside that guest logical clock.

FOUNDATION / 03

An address belongs to an address space.

When a Rust program holds a pointer, its numeric value is usually a virtual address. Two processes can use the same number and still refer to different physical memory.

The operating system creates an address space for each process. Page tables are the data structure describing how virtual pages map to physical frames, along with access permissions. Switching a process typically changes which page-table root is active. In x86-64 that root is selected through CR3. This is why a raw pointer value is insufficient to identify actual RAM: its meaning depends on the current address space.

For each memory access, paging hardware either finds a permitted mapping or reports a page fault, written #PF. A page fault is normally an event for the guest operating system: perhaps the page has not been allocated yet, perhaps it is a copy-on-write page, or perhaps the access is invalid. The OS may install a mapping and retry, or may terminate the process. Neither outcome inherently involves a VM exit.

Permissions matter independently of the address itself. A page can be readable but not writable, or non-executable so instruction fetch is forbidden. Those distinctions will later let Bedrock use the hardware as a guard: it can allow a data read while stopping a code fetch from a page whose behavior it has not yet proven safe. [Intel SDM, AMD APM]

Why the operating system gives processes separate address spaces

Separate address spaces provide isolation and a useful programming illusion. Process A can place its code, stack and heap at convenient virtual addresses without coordinating raw RAM locations with process B. The kernel maps those virtual pages to frames it owns and sets permissions. It may map a shared library into both processes, map a read-only file into many processes, or give each process a private writable copy. The same virtual pointer value can therefore mean different data under different CR3 roots, as the animation shows; conversely, two different virtual pointers can intentionally name the same physical frame.

On a context switch, Linux changes which process is running and which page-table root is active. The TLB may retain translations tagged by an address-space identity, but an entry must never be used under the wrong context. Virtualization does not remove this guest mechanism. Bedrock runs a Linux guest that schedules its own processes, changes guest CR3, takes guest page faults and manages guest virtual memory. The host owns a second, independent mapping from the guest's invented physical frames to actual host frames.

Copy-on-write shows why permissions are active machinery, not merely annotations. A parent and child can initially refer to the same physical page while both mappings are read-only. When one tries to write, a fault lets software allocate a private copy and update its mapping. Bedrock uses a related host-level copy-on-write technique for forked VM states. The guest's own page fault and the host's nested-memory fault are different layers of that story, and the performance cost depends on which layer catches a particular write.

FOUNDATION / 04

How does a pointer reach RAM?

A virtual address does not contain a physical address. The CPU follows page-table entries to find a physical frame, checks permissions, and then adds the offset within the page.

For common four-level x86-64 paging, the virtual address is divided into several indexes plus a page offset. Starting at the root named by CR3, hardware reads a top-level entry, then lower-level entries, until it reaches a leaf mapping. With 4 KiB pages, the low 12 address bits are the offset. Large pages can stop the walk earlier. Each entry may restrict permission; a missing or forbidden mapping causes #PF. The CPU may perform parts of this walk speculatively, but the resulting access must satisfy the architectural checks.

A toy page table you can calculate by hand

To make the data structure tangible, imagine a tiny machine with 16-bit virtual addresses and 256-byte pages. The low eight bits of an address are the offset within its page. The high eight bits choose a virtual page. Suppose page 0x12 maps to physical frame 0xA0. Address 0x1234 then reaches physical address 0xA034: the mapping replaces the page number while preserving the offset 0x34. If page 0x1A maps to frame 0xB0, then 0x1A34 reaches 0xB034. Real x86-64 paging uses several levels and normally 4 KiB pages, but the frame-plus-offset operation is the same.

A page-table entry is therefore not merely an address pointer. It also carries flags. If the toy entry is read-only, a read succeeds but a write faults even though the translation exists. If no entry maps page 0x20, the CPU cannot infer a physical frame and raises a page fault. The guest kernel can respond by allocating memory, loading a page or rejecting the access. This is why a “page fault” can be part of normal demand paging rather than necessarily a bug. The next virtualization layer adds a second independent mapping after this guest translation.

A full walk can require multiple memory reads, so processors cache completed translations in a translation lookaside buffer (TLB) and may cache intermediate walk information too. A TLB hit avoids repeating the walk. This is a major reason why paging is practical at high speed. It is also why changing a page-table entry requires care: a stale cached translation must be invalidated before the new mapping can be relied upon.

Translation and caching are different questions. The page table says what mapping is authoritative. The TLB accelerates repeated use of that mapping. Later, Intel VPID and AMD ASID will be much easier to understand: they are tags that help the CPU distinguish cached translations belonging to different guest contexts. They do not grant permission, and they do not make a changed mapping magically current. [Intel SDM, AMD APM]

FOUNDATION / 05

Not every stop is a VM exit.

An exception, interrupt, system call and VM exit all redirect execution. They differ in who requested the redirect, when it occurs, and who handles it.

A system call is a program intentionally asking the kernel for a service. A page fault is a synchronous exception from a specific memory access. A hardware interrupt generally announces an external or asynchronous event. A VM exit transfers from guest execution to the hypervisor because a virtualization control or second-stage memory rule requires it. A guest can see its own page fault and handle it without the hypervisor emulating every step. Conversely, a nested-memory denial returns to the hypervisor even if the guest's own page tables would allow the access.

These boundaries compose. A guest application may execute a system call; the guest kernel then touches a page that the hypervisor has marked read-only; that second access may cause a VM exit. The hypervisor can modify the second-stage mapping and resume the guest kernel, which may finish the original system call. If we count every one of these as the same kind of “trap,” we lose the reason a particular workload is slow.

Bedrock's key performance counter is therefore the number of host returns caused by the virtualization boundary. A guest-internal page fault still costs guest work, but a VM exit also incurs a hardware world switch plus Bedrock's host-side bookkeeping. [Intel SDM, AMD APM]

What the CPU actually does on SYSCALL

On x86-64, SYSCALL is an instruction, not a library call to another userspace function. The application executes it with a syscall number and arguments arranged according to its operating-system ABI. The CPU saves a return instruction pointer and selected flags in architecturally specified registers, loads the kernel entry address from a privileged MSR, changes privilege state, and begins executing the kernel entry code. The kernel's entry assembly establishes a safe kernel stack and saves the register context it needs. Linux dispatches the requested operation, then returns through an appropriate instruction path so application execution continues at the saved point. This happens on the same physical core. The hypervisor does not need to emulate every syscall merely because the guest changed from CPL3 to CPL0. [Intel SDM, SYSCALL/SYSRET and privilege transitions, AMD APM, SYSCALL/SYSRET]

The stack detail is a good example of why a real control-flow diagram matters. The application stack belongs to userspace and cannot simply be trusted as a kernel working stack. The CPU's SYSCALL transition does not by itself create a complete high-level Rust call frame. The kernel entry code switches to its own stack, saves context, handles the service, and constructs the return. In the visual scene above, the highlighted kernel stack appears only after the core has crossed into guest-kernel execution. Bedrock still remains in the host lane, idle, unless a separate virtualization control trips.

A page fault is a retry point; a VM exit is a different boundary

Suppose the userspace instruction mov rax, [rbx] references an unmapped virtual page. The CPU's guest page-table walk cannot produce a permitted translation. It raises #PF, records the faulting address and fault information, and enters Linux's guest page-fault handler. The load has not retired. If Linux allocates or maps the page, returning from the handler retries the same instruction at its original RIP. If the address is invalid, Linux may signal or terminate the process. The same guest-internal exception mechanism also handles many copy-on-write page faults. None of this necessarily crosses into Bedrock.

Now suppose the guest page table permits the access, but Bedrock's EPT or NPT mapping denies it. The denial belongs to the second-stage translation. Hardware exits to the host and reports a nested-memory failure. The guest Linux page-fault handler does not initially receive this event, because its own mapping was valid. Bedrock may use the host return to maintain copy-on-write state, catch a code write or build a safe execution region. It then resumes the guest, often at the same RIP so the stopped access can retry after the host has changed its mapping. This is why the memory scene shows the two permission layers separately.

An interrupt is a delivery decision, not an instruction request

A hardware timer or virtual device can make an interrupt pending independently of the guest's next instruction. The CPU may deliver it when architectural conditions allow, saving the interrupted context and entering the guest handler. Linux then runs its timer and scheduler code. A deterministic test cares about exactly which guest instructions retired before delivery. Bedrock controls the virtual event schedule and must stop guest execution at the intended logical boundary before making the timer visible. The underlying CPU may have efficient interrupt-delivery hardware, but “efficient” is not the same as “delivered at Bedrock's chosen retired-instruction count.”

These paths can nest. A guest application may execute SYSCALL, the kernel may take a guest page fault while copying an argument, and a virtual timer may become pending before the syscall completes. Bedrock's job is not to replace Linux's normal exception machinery. It is to control the host-visible boundaries and outside inputs so that this nested history can be reproduced. When we discuss performance later, we count VM exits separately from work Linux performs within its guest mode.
