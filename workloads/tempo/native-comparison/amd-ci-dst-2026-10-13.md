# AMD run of the current Tempo DST CI workload (2026-10-13)

The Intel control is [Tempo E2E run 38431442041](https://github.com/tempoxyz/bedrock/actions/runs/38431442041), using `tempoxyz/bedrock` commit `f6f885a89d345359713169248b37ef5627b84ae9`, Tempo `b73522c36dd5b0c7aea7e58941d990487f508566`, txgen `00fb4e03c187954df676e3fc49bcc71c6c865883`, two validators, consensus enabled, one seed (`14373434789495652599`). CI reports **65 host seconds** for its passing one-seed campaign (55.38 seeds/hour). The complete GitHub job was 5m14s including builds.

The same container images, compose file, planner, seed, topology, workload command (`podman exec tempo-dst /usr/local/bin/tempo-dst`), and host-side `bedrock-dst` revision were prepared locally from that commit. All module operations and AMD executions used disposable `boxctl` box `box-9781f391` (AMD EPYC 4245P, Ubuntu HWE `7.0.0-38-generic`). The local workstation built only userland and Nix guest artifacts; it did not build or load a kernel module.

An identical upstream guest kernel/initrd did not boot successfully under this AMD branch: PID 1 exited with code 1, then the kernel entered `vpanic`'s delay loop. A 318-second control and a 188-second run with stable guest RAM did not reach the workload. The latter removed repeated page-hazard scanning from the profile but did not address the boot failure. The upstream kernel also lacks the AMD branch's `bedrock_loop_delay` option, so its `delay_tsc` path repeatedly exits for emulated RDTSC.

With the AMD branch's `guestKernel`, `amdTempoInitrd`, and `bedrock_loop_delay lpj=1000000`, the same containers and seed booted, loaded the images, and ran Tempo. The guest reached approximately 184 seconds of virtual time but did not reach the campaign ready checkpoint before a **180-host-second cap**. This is a lower bound of **2.77× the Intel campaign's completed wall time**, not an AMD completion time. At the cap, the diagnostic counters included 56.5 million nested-page violations, 14.3 million synthetic step exits, 1.58 million RDTSC and 3.81 million RDTSCP exits. The guest's reported `emulated_tsc` stays stale on nondeterministic host-interrupt exits; a kernel probe confirmed retired-instruction accounting continued during those intervals, so a flat progress readout alone is not evidence of a hang.

The AMD trial used the current-main `bedrock-dst` driver with the branch's stable-memory ioctl support and a diagnostic boot-progress print. The branch now seals guest RAM immediately after `setup_linux_boot`; this enables retention of code and page-table proofs across userspace exits. The source changes also add a bounded native path for a pure 64-bit `DEC RAX; JNZ` loop. A box hardware test verified 200,000 exact guest instructions, a mid-loop stop-at-TSC deadline, and final RAX/flags in 1.8 ms. That loop improvement did not change this CI run's dominant path: the Linux delay loop observed after 5.4 guest seconds in the initial AMD-kernel trial was the *panic* loop, caused by the mismatched initrd.

The next run identified the readiness blocker precisely: the byte-identical CI `bedrock-ready` helper is prebuilt with Intel `VMCALL` and trapped with #UD on AMD just after it logged that validators were producing blocks. The AMD executor now accepts that exact three-byte opcode as a hypercall while leaving other #UD faults alone. A box hardware test confirmed `HYPERCALL_READY` and the resulting RIP. With this fix, the unchanged CI container images reached READY at guest virtual 39–47 seconds across runs.

After READY, the driver forks the VM for warmup. The first fork retained no stable-memory proof, so it repeatedly rebuilt page and alias proofs. The branch now propagates a sealed parent's state through `Vm::fork`, accepts the stable-memory run ioctl on forked VMs, and seals the ready checkpoint after protecting any writable file-transfer feedback mapping. Mutable access unseals both guest RAM and writable feedback mappings. A forked-VM hardware test passed 10,001 deterministic guest instructions in 0.7 ms. On the full CI workload, however, the resealed run still spent minutes before its first ten-virtual-second warmup hook. A post-READY host profile sampled roughly 34% in `collect_page_breakpoints`, 18% in root-page reads, 16% in fork-page reads, 15% in `__pi_memcpy`, and 10% in translation-tree collection, with less than 1% in `svm_run_guest`. The 900-second campaign was stopped early because this path could not yet yield a useful one-seed completion time.

The TSC-delay option was tested separately on the same box with the same guest artifacts and CI workload, changing only the guest command line. Near 31.5 virtual seconds, the run **with** `bedrock_loop_delay` had 269,034 RDTSC exits, 980,702 RDTSCP exits, and 38.40 million NPT violations; the run **without** it had 267,836 RDTSC exits, 1,037,641 RDTSCP exits, and 38.39 million NPT violations. Both reached READY after about two host minutes. Thus disabling the kernel's `delay_tsc` polling matters for its panic-loop case, but it is not the cause of the healthy CI workload's much larger slowdown. Guest userspace time reads still cause RDTSCP exits, while the measured host CPU cost is dominated by proof collection.

The post-READY fork slowdown had another general cause: inherited read-only COW NPT leaves returned `None` from `restrict_write_4k`, so page-table guards could not be retained and alias proofs were discarded on each run. `NptWriteGuard` now represents an already read-only mapping without making it writable on restoration. A disposable-box hardware suite and the EPT, VMX, and VM unit suites pass. In an instrumented exact-workload run, alias-proof cache hits continued increasing after the fork instead of freezing. A 360-host-second campaign reached READY at 46.4 virtual seconds, completed warmup and created its warm checkpoint at 62.1 virtual seconds, then advanced the seed to about 81.4 virtual seconds before the cap. The same Intel campaign completed its seed in 65 host seconds, so AMD has a measured lower bound of **more than 5.5 times** the Intel wall time and still has no completed seed timing. Proof walks and invalidations remain frequent after this fix; profile and reduce that residual cost before claiming performance parity.

The AMD result is an operational comparison of each side's intended guest bundle, not a byte-identical kernel/initrd A/B test. The TSC-delay option is a separate, tested panic-loop fix and does not explain the healthy workload's remaining slowdown.

A later seed-phase `perf` sample on the forked VM assigned about 21% of CPU to `collect_page_breakpoints`, 8% to parent-page lookup, and 5% to actual `svm_run_guest`; the hot instructions in breakpoint collection scan guest page-table entries. Using the existing guarded-table hash index for upper-level lookups had no clear effect on this profile or capped campaign and was discarded. Reading each table page in two 2KB chunks instead of eight 512-byte chunks reduced the sampled parent-page lookup share to about 5%, but a 360-second exact-workload run still advanced only about 25 virtual seconds into the seed. This is a bounded read overhead reduction, not a completed Intel-comparable campaign.

After the read-only fork guard fix, an additional conservative code-page filter keeps guarded alias proofs across forked COW changes to ordinary data pages. It only treats a remap as unrelated when its GPA is outside the active and retained page-table sets and outside the possible-code filter. This reduced repeated global guard rebuilds from tens of thousands to roughly 3,200 in a comparable capped run. A seed-phase `perf` sample then assigned about 11.5% of CPU to `collect_page_breakpoints`, 10.5% to NPT `restrict_write_4k`, 6.8% to `svm_run_guest`, 6.7% to `bedrock_phys_to_virt`, and 6.6% to `page_hazards`.

The exact one-seed campaign completed on disposable box `box-2a8db29e` (EPYC 4245P, HWE `7.0.0-38-generic`) with the pushed `63514bd` module. Seed `14373434789495652599` **passed** with no failures and timeline `tl-1457747015ab3105`. The seed took 872 host seconds; the full campaign, including boot and warmup, took **1,027 host seconds** (3.50 seeds/hour). Against the Intel CI campaign's 65 host seconds, this is **15.8× the elapsed time**. This compares complete passing campaigns but includes different host hardware and each branch's intended guest kernel/initrd; it is not an isolated AMD-versus-Intel CPU measurement. The general COW fix establishes correctness and cuts proof rebuilds, but does not yet bring the Tempo workload close to the Intel timing.

Two follow-up NPT write-guard location caches passed the EPT and VMX library tests and the disposable-box hardware suite, but did not help the Tempo campaign. A direct-mapped cache keyed by each 4KB page completed the same seed with a passing verdict in **1,150 host seconds** on another EPYC 4245P/HWE box (`box-7df741a2`), about 12% slower than the 1,027-second baseline. Its miss path occupied about 9% of sampled CPU in addition to roughly 10% in `restrict_write_4k`. Keying instead by the 2MB region shared by 512 PTEs removed that extra miss-path hotspot, but on the **same box as the baseline** it reached roughly 110 virtual seconds after 500 host seconds, whereas the baseline had reached 109 virtual seconds after 457 host seconds. The region run was stopped after 525 host seconds; its seed profile still had about 10% in `restrict_write_4k`. Both cache variants were discarded. Reducing the cost of that one function is insufficient to close the 15.8× campaign gap while proof and NPT exits remain frequent.

The next change captures the kernel's KASLR-adjusted x86 direct-map base once at module initialization and computes `phys_to_virt` by adding the physical address in Rust. Previously each nested-page-table frame lookup crossed into a C `__va` helper. Two disposable-box hardware suites passed. A bounded exact-seed diagnostic covering 40 virtual seconds took 183.3 host seconds with this change, versus 225.8 and 221.3 seconds in baseline runs on the same box; entry cycles per exit fell from about 19.2–19.7k to 15.3k. The warm checkpoints varied, so these diagnostic spans are supporting evidence rather than an exact A/B.

The unmodified `bedrock-dst` binary then completed the full one-seed campaign with the direct-map change on the **same box as the 1,027-second baseline** (`box-2a8db29e`): the seed **passed** in 715 host seconds and the campaign in **872 host seconds** (4.13 seeds/hour), with no failures and timeline `tl-5595fa6e0585b75b`. This is about **15% less campaign wall time** than the baseline and still **13.4× the Intel CI campaign's 65 host seconds**. A second EPYC 4245P/HWE box (`box-7df741a2`) also passed the same seed, in 884 host seconds and 1,052 campaign seconds; that cross-box variation is why the same-box comparison is primary. The gain is general per-exit translation overhead reduction, while the remaining tens of millions of NPT and synthetic step exits still dominate.

A disposable-box diagnostic then counted execute NPT faults over guest TSC 180–240 billion in the **exact CI seed**. It counted **11,431,596** faults on 3,858 physical pages, with no histogram drops. The hottest page alone caused 1,859,460 faults (16.3%); the top five caused 4,572,147 (40.0%); the top ten caused 5,886,439 (51.5%). The first three page-start fingerprints match code in the pinned OCI glibc, though some sequences also occur in bundled executables, so the 16-byte matches do not uniquely identify their owner. This concentration differs from the earlier shaped 10,000-transfer workload, whose top ten pages caused only 22.9% of execute faults. A seed-phase host `perf` sample assigned about 11.9% to `protect` and 11.7% to `collect_page_breakpoints` after the direct-map change. The histogram build passed the box hardware suite and was stopped after collecting the window; it is diagnostic only and is not included in the pushed performance code. The next high-leverage experiment should inspect the actual hazard entries and false masked hits on these exact CI pages before relaxing any guard.

Two bounded follow-ups used the same box and exact CI seed. An isolated planner candidate eagerly merged the two `REP MOVSB` hazards at offsets `0xc64` and `0xcca` on the hottest libc page into one masked breakpoint. It passed 272 VMX tests and the box hardware suite, but took **228.9 host seconds** for a 40-virtual-second seed span, versus **183.3 seconds** for the direct-map control. It reduced some NPT faults while increasing entry cycles and was rejected. A second candidate hid AVX2 from AMD guests through CPUID, leaving the existing ERMS mask intact. It passed 270 VMX tests and the box suite. Its first 50-virtual-second diagnostic span looked slightly faster, but the full unmodified CI campaign was **still running at 895 host seconds** and had reached only about 211 virtual seconds; the control had already passed the complete campaign in 872 seconds. It was stopped and rejected. Both changes were removed from the branch. The diagnostic builds were loaded only inside the disposable box.

A final diagnostic sampled one in 4,096 execute NPT faults over guest TSC 180–240 billion and retained 146 entries on the same hottest libc code page (its physical address changed across runs, so the sampler matched its 16-byte page start). Of these entries, **118 were at offset `0x930`** and **25 at `0x260`**; only three other offsets appeared once each. The page-table gate was ready and clean in all samples. Disassembly of the pinned libc shows that `0x930` enters a vectorized copy routine, while its guarded `REP MOVSB` instructions are at `0xc64` and `0xcca` on larger-copy paths. Entry samples do not prove those REP instructions are never reached; they show that ordinary entries to a page containing two real REP sites account for many execute faults. This points to a general guarded-code execution problem rather than a missing gate or one bad mask. The diagnostic patch was removed after collection; raw samples are in ignored `target/boxctl-evidence/box-2a8db29e/ci-glibc-entry-dmesg.txt`.

A second diagnostic saw about **945,000** guarded breakpoint replay events across the guest in the same broad virtual-time window, but no matched replay on that libc page. This has a limitation: the page was identified by its bytes in the earlier execute-fault run, while the breakpoint probe was a separate run and did not independently count that page's execute faults. It is suggestive, not proof that the REP sites never execute.

Allowing the existing bounded reachable-region proof on general two-hazard pages passed 270 VMX tests and the in-box suite, but the exact CI seed took **188.4** host seconds for a 40-virtual-second span, versus **183.3** seconds for the direct-map control. It also produced about 0.79 million more NPT faults and 1.05 million more total exits. The candidate was removed. A follow-up diagnostic identified the hot page by its first 16 bytes and counted **983,040** of its execute faults in the measurement window. At that point `prepare_global_into` had been called **1,040,709** times for that page and had succeeded **994,010** times; early eligibility checks rejected 30,789, the deadline margin rejected 15,910, and cached hazard and alias proofs rejected **zero**. The recurring cost is therefore not inability to construct the global plan. The current batch guard restores nested execute permissions after each exit, so repeated entries to this page continue to fault and re-arm a plan. Any retained-execution optimization must preserve the same code-write, page-table, alias, and debug-breakpoint invariants across exits. Diagnostic source was removed after collection; counters are in ignored `target/boxctl-evidence/box-2a8db29e/ci-hot-planner-dmesg.txt`.

An exit-reason probe on the same byte-identified libc page counted **1,769,472** successful global guarded runs during the guest-TSC 180–240-billion window. Of these, **1,716,634 (97.0%)** exited on an execute NPT fault, 2,743 on a write NPT fault, 5,523 on a monitor trap, and the remainder on exceptions or other exits. This is a bounded diagnostic run, not a campaign timing. It shows that retaining the guard only across interrupts or deadline events cannot eliminate most of this page's repeated exits: execution usually transfers to another code page first.

A second bounded probe sampled one in 4,096 execute-fault destinations from that libc page in the same guest-TSC window. Its **135** retained samples covered **70** distinct guest-physical pages; the most frequent destinations had only **10** samples each. All 135 destinations had `npt_trusted_code_4k=false` (the trusted bit is independent of the guard's temporary NX setting). The current planner already attempts to admit predicted and recently visited hazardous pages if their combined breakpoints and alias proofs fit. Adding globally trusted pages to this guard would not address these sampled transfers; permitting arbitrary hazardous destinations would lose the exact-execution proof. The two probe runs were stopped at fixed host-time caps, and their diagnostic source was removed. Raw counters and samples are in ignored `target/boxctl-evidence/box-2a8db29e/ci-hot-target-dmesg.txt`.

A fresh 60-second host `perf` sample of the **clean pushed module** during the forked CI seed captured 5,967 cycle samples with none lost. The leading flat symbols were `collect_page_breakpoints` (11.08%), `protect` (10.44%), `svm_run_guest` (9.49%), fork-parent `read_page` (6.15%), `page_hazards` (5.33%), batch-guard restore (5.11%), root-parent `read_page` (4.29%), and NPT execution restriction (3.81%). These are sample shares, not additive improvement forecasts. The raw profile and report are in ignored `target/boxctl-evidence/box-2a8db29e/perf-ci-clean.data` and `perf-ci-clean-report.txt`.

An isolated cache probe then logged alias-proof outcomes every 1,048,576 requests during the exact CI workload. At 62,914,560 requests, the 2,048-entry control cache had 788,982 full alias walks and 530,069 lookups that found another valid proof in the chosen set. Doubling capacity to 4,096 entries reduced these to 737,383 walks (6.5%) and 143,968 valid-set misses (72.8%) at the same request count. Both variants passed 270 VMX unit tests and the box hardware suite. Their 241-second bounded campaigns reached different warm checkpoints (virtual 48.2 versus 53.8 seconds), so the equal-host-time data does **not** establish a wall-time gain. Most walks remained despite the larger cache, and it adds roughly half a megabyte per VM; the capacity change was removed. Diagnostic source was also removed. Counter logs are in ignored `target/boxctl-evidence/box-2a8db29e/ci-proof-cache-dmesg.txt` and `ci-proof-4096-dmesg.txt`.

Two more bounded exact-seed traces tested whether the hot libc page's NPT exits could be avoided by choosing better companion pages. In the first, **111 of 138** sampled execute-fault runs already had all four hardware breakpoint slots occupied. The second recorded the exit RIP and the guest word at `RSP-8`; **117 of 137** execute-fault samples used all four slots, **34** had a popped word equal to the faulting RIP (consistent with a return), and **52** landed on one of the two most recently visited linear pages. These samples show that a better choice can sometimes replace a wrong companion, but a guard cannot simply add another hazardous page. The popped-word test is a heuristic rather than a complete call/return trace. Logs are in ignored `target/boxctl-evidence/box-2a8db29e/ci-return-plan-dmesg.txt` and `ci-return-rip-dmesg.txt`.

A general ordering candidate admitted the immediate prior page before the predicted successor when composing a guarded global batch; all alias, hazard, and breakpoint checks were unchanged. It passed 270 VMX unit tests and the disposable-box hardware suite. The full exact-CI campaign on the same EPYC/HWE box was **still running after 934 host seconds**, while the pushed control had completed and passed in **872 seconds**. The candidate was stopped without a seed verdict and removed. A simple priority swap does not close the performance gap; more useful guard residency would require a way to keep the chosen page protected and its breakpoint proof valid across exits.

The next experiment tried to avoid a redundant NPT write-protection walk during global guarded entries when a hot code page already had a persistent recurrent-code write guard. The first variant searched the hazard-memo table to confirm the guard; it passed 270 VMX tests and the in-box hardware suite but was **still in the seed after 947 host seconds**, versus the control's passing 872-second campaign. A second variant checked only the direct lookup hint and fell back to the original write-protection walk on a miss. A focused test covered both the hint hit and stale-hint fallback, and the box suite passed. A 60-second seed-phase `perf` sample captured 5,960 cycle samples with no losses: `protect` still took **10.16%** of flat samples, versus **10.44%** in the clean control profile. These profiles are from separate runs, so the 0.28-point difference is not a measured speedup. The bounded run was stopped at 252 host seconds; neither candidate was merged. The hint profile and status are in ignored `target/boxctl-evidence/box-2a8db29e/perf-ci-hint.data`, `perf-ci-hint-report.txt`, and `ci-hint-perf-status.txt`.

On 2026-10-14, a larger recurrent-code hazard memo was tested on the same box: 256 to 512 memo slots, 1,024 to 2,048 lookup hints, 64 to 128 guarded hints, and 192 to 384 ordinary persistent write guards (with the replacement test scaled accordingly). The VMX library tests and disposable-box hardware suite passed. A 60-second exact-seed `perf` sample had 5,961 cycles samples and none lost. Its flat `page_hazards` share fell from 5.33% in the clean control profile to 2.50%, and `collect_page_breakpoints` from 11.08% to 7.98%; `svm_run_guest` rose from 9.49% to 12.55%. These relative shares did not translate into a useful campaign result: the exact one-seed run was **still in the seed at 1,015 host seconds** when stopped, while the same-box pushed control had **passed at 872 seconds**. The capacity change was removed. The bounded campaign status and raw profile are in ignored `target/boxctl-evidence/box-2a8db29e/` and the box's `/home/ubuntu/ci-dst/`.

A shadow global-plan cache diagnostic on the exact seed then found that about 28% of successful plans repeated with the same code, translation, and selected-page state over the sampled seed minute. A guarded 512-slot implementation reused those plans only while the code write guards, NPT mapping, trusted-code generation, page-table generation, and recent-page prediction still matched. It passed 271 VMX tests, including a cache-invalidation test, and the disposable-box hardware suite. Its complete exact one-seed campaign **passed in 933 host seconds** (790-second seed). A fresh run of the restored pushed control on the **same box** passed in **970 host seconds** (825-second seed), but an earlier control on that box passed in **872 host seconds** (715-second seed). The observed run variation is larger than the apparent 37-second cache advantage; the cache did not establish a reliable wall-time gain and was removed. A perf-attached candidate run aborted just after seed start with a bounded-PMU check; a subsequent unprofiled candidate run passed, so that failure's cause was not isolated. The raw candidate profile, shadow-hit log, and campaign statuses are in ignored `target/boxctl-evidence/box-2a8db29e/` and the box's `/home/ubuntu/ci-dst/`. Repeated page exits, not merely repeated planning, remain the main performance target.

A return-target predictor then tried to reduce those execute NPT faults without changing the guest. On a return-like global-batch exit (execute fault at another linear page with RSP advanced by eight bytes), it remembered the destination under the guarded CR3, source page, and entry RSP. The next entry considered that page before the existing successor and recent-page candidates; unchanged hazard, alias, and four-breakpoint checks still controlled admission. The VMX library tests and disposable-box SVM suite passed. A shortened 60-virtual-second seed initially seemed promising as a faster feedback loop, but its control **failed** the workload's container-exit assertion in 470 host seconds while the predictor variant **passed** in 516 seconds; their warm checkpoints were also at different virtual times (54.4 versus 71.9 seconds). That shortened campaign is therefore not a reliable performance or correctness comparison for this change. In the exact 180-second campaign, the predictor was **still in the seed at 1,097 host seconds** when stopped, beyond both completed same-box controls (872 and 970 seconds). It was removed. Raw statuses remain on `box-2a8db29e` under `/home/ubuntu/ci-dst/`. The sampled hot-page exits had suggested a limited ceiling: only 34 of 137 execute-fault samples looked like returns, and 25 of those already used all four breakpoint slots, so a return predictor often has to displace another guarded page rather than add one.
