# AMD run of the current Tempo DST CI workload (2026-10-13)

The Intel control is [Tempo E2E run 38431442041](https://github.com/tempoxyz/bedrock/actions/runs/38431442041), using `tempoxyz/bedrock` commit `f6f885a89d345359713169248b37ef5627b84ae9`, Tempo `b73522c36dd5b0c7aea7e58941d990487f508566`, txgen `00fb4e03c187954df676e3fc49bcc71c6c865883`, two validators, consensus enabled, one seed (`14373434789495652599`). CI reports **65 host seconds** for its passing one-seed campaign (55.38 seeds/hour). The complete GitHub job was 5m14s including builds.

**Current AMD result (2026-10-14): 253 host seconds, including a 199-second seed, with the userspace driver rebuilt from this branch and the production module.** This is about **3.9×** the Intel campaign's 65 seconds on different hardware and guest kernels. Earlier 310–331-second results below used an October 13 staged `bedrock-dst` executable that predated branch userspace changes and are superseded as measurements of the current branch. The detailed provenance check is at the end of this log.

The same container images, compose file, planner, seed, topology, workload command (`podman exec tempo-dst /usr/local/bin/tempo-dst`), and host-side `bedrock-dst` revision were prepared locally from that commit. All module operations and AMD executions used disposable `boxctl` box `box-9781f391` (AMD EPYC 4245P, Ubuntu HWE `7.0.0-38-generic`). The local workstation built only userland and Nix guest artifacts; it did not build or load a kernel module.

An identical upstream guest kernel/initrd did not boot successfully under this AMD branch: PID 1 exited with code 1, then the kernel entered `vpanic`'s delay loop. A 318-second control and a 188-second run with stable guest RAM did not reach the workload. The latter removed repeated page-hazard scanning from the profile but did not address the boot failure. The upstream kernel also lacks the AMD branch's `bedrock_loop_delay` option, so its `delay_tsc` path repeatedly exits for emulated RDTSC.

With the AMD branch's `guestKernel`, `amdTempoInitrd`, and `bedrock_loop_delay lpj=1000000`, the same containers and seed booted, loaded the images, and ran Tempo. The guest reached approximately 184 seconds of virtual time but did not reach the campaign ready checkpoint before a **180-host-second cap**. This is a lower bound of **2.77× the Intel campaign's completed wall time**, not an AMD completion time. At the cap, the diagnostic counters included 56.5 million nested-page violations, 14.3 million synthetic step exits, 1.58 million RDTSC and 3.81 million RDTSCP exits. The guest's reported `emulated_tsc` stays stale on nondeterministic host-interrupt exits; a kernel probe confirmed retired-instruction accounting continued during those intervals, so a flat progress readout alone is not evidence of a hang.

The AMD trial used the current-main `bedrock-dst` driver with the branch's stable-memory ioctl support and a diagnostic boot-progress print. The branch now seals guest RAM immediately after `setup_linux_boot`; this enables retention of code and page-table proofs across userspace exits. The source changes also add a bounded native path for a pure 64-bit `DEC RAX; JNZ` loop. A box hardware test verified 200,000 exact guest instructions, a mid-loop stop-at-TSC deadline, and final RAX/flags in 1.8 ms. That loop improvement did not change this CI run's dominant path: the Linux delay loop observed after 5.4 guest seconds in the initial AMD-kernel trial was the *panic* loop, caused by the mismatched initrd.

The next run identified the readiness blocker precisely: the byte-identical CI `bedrock-ready` helper is prebuilt with Intel `VMCALL` and trapped with #UD on AMD just after it logged that validators were producing blocks. The AMD executor now accepts that exact three-byte opcode as a hypercall while leaving other #UD faults alone. A box hardware test confirmed `HYPERCALL_READY` and the resulting RIP. With this fix, the unchanged CI container images reached READY at guest virtual 39–47 seconds across runs.

After READY, the driver forks the VM for warmup. The first fork retained no stable-memory proof, so it repeatedly rebuilt page and alias proofs. The branch now propagates a sealed parent's state through `Vm::fork`, accepts the stable-memory run ioctl on forked VMs, and seals the ready checkpoint after protecting any writable file-transfer feedback mapping. Mutable access unseals both guest RAM and writable feedback mappings. A forked-VM hardware test passed 10,001 deterministic guest instructions in 0.7 ms. On the full CI workload, however, the resealed run still spent minutes before its first ten-virtual-second warmup hook. A post-READY host profile sampled roughly 34% in `collect_page_breakpoints`, 18% in root-page reads, 16% in fork-page reads, 15% in `__pi_memcpy`, and 10% in translation-tree collection, with less than 1% in `svm_run_guest`. The 900-second campaign was stopped early because this path could not yet yield a useful one-seed completion time.

The TSC-delay option was tested separately on the same box with the same guest artifacts and CI workload, changing only the guest command line. Near 31.5 virtual seconds, the run **with** `bedrock_loop_delay` had 269,034 RDTSC exits, 980,702 RDTSCP exits, and 38.40 million NPT violations; the run **without** it had 267,836 RDTSC exits, 1,037,641 RDTSCP exits, and 38.39 million NPT violations. Both reached READY after about two host minutes. Thus disabling the kernel's `delay_tsc` polling matters for its panic-loop case, but it is not the cause of the healthy CI workload's much larger slowdown. Guest userspace time reads still cause RDTSCP exits, while the measured host CPU cost is dominated by proof collection.

The post-READY fork slowdown had another general cause: inherited read-only COW NPT leaves returned `None` from `restrict_write_4k`, so page-table guards could not be retained and alias proofs were discarded on each run. `NptWriteGuard` now represents an already read-only mapping without making it writable on restoration. A disposable-box hardware suite and the EPT, VMX, and VM unit suites pass. In an instrumented exact-workload run, alias-proof cache hits continued increasing after the fork instead of freezing. A 360-host-second campaign reached READY at 46.4 virtual seconds, completed warmup and created its warm checkpoint at 62.1 virtual seconds, then advanced the seed to about 81.4 virtual seconds before the cap. The same Intel campaign completed its seed in 65 host seconds, so AMD has a measured lower bound of **more than 5.5 times** the Intel wall time and still has no completed seed timing. Proof walks and invalidations remain frequent after this fix; profile and reduce that residual cost before claiming performance parity.

The AMD result is an operational comparison of each side's intended guest bundle, not a byte-identical kernel/initrd A/B test. The TSC-delay option is a separate, tested panic-loop fix and does not explain the healthy workload's remaining slowdown.

A later seed-phase `perf` sample on the forked VM assigned about 21% of CPU to `collect_page_breakpoints`, 8% to parent-page lookup, and 5% to actual `svm_run_guest`; the hot instructions in breakpoint collection scan guest page-table entries. Using the existing guarded-table hash index for upper-level lookups had no clear effect on this profile or capped campaign and was discarded. Reading each table page in two 2KB chunks instead of eight 512-byte chunks reduced the sampled parent-page lookup share to about 5%, but a 360-second exact-workload run still advanced only about 25 virtual seconds into the seed. This is a bounded read overhead reduction, not a completed Intel-comparable campaign.

After the read-only fork guard fix, an additional conservative code-page filter keeps guarded alias proofs across forked COW changes to ordinary data pages. It only treats a remap as unrelated when its GPA is outside the active and retained page-table sets and outside the possible-code filter. This reduced repeated global guard rebuilds from tens of thousands to roughly 3,200 in a comparable capped run. A seed-phase `perf` sample then assigned about 11.5% of CPU to `collect_page_breakpoints`, 10.5% to NPT `restrict_write_4k`, 6.8% to `svm_run_guest`, 6.7% to `bedrock_phys_to_virt`, and 6.6% to `page_hazards`.

The exact one-seed campaign completed on disposable box `box-2a8db29e` (EPYC 4245P, HWE `7.0.0-38-generic`) with the pushed `63514bd` module. Seed `14373434789495652599` **passed** with no failures and timeline `tl-1457747015ab3105`. The seed took 872 host seconds; the full campaign, including boot and warmup, took **1,027 host seconds** (3.50 seeds/hour). Against the Intel CI campaign's 65 host seconds, this is **15.8× the elapsed time**. This compares complete passing campaigns but includes different host hardware and each branch's intended guest kernel/initrd; it is not an isolated AMD-versus-Intel CPU measurement. The general COW fix establishes correctness and cuts proof rebuilds, but does not yet bring the Tempo workload close to the Intel timing.

Two follow-up NPT write-guard location caches passed the EPT and VMX library tests and the disposable-box hardware suite, but did not help the Tempo campaign. A direct-mapped cache keyed by each 4KB page completed the same seed with a passing verdict in **1,150 host seconds** on another EPYC 4245P/HWE box (`box-7df741a2`), about 12% slower than the 1,027-second baseline. The next change captures the kernel's KASLR-adjusted x86 direct-map base once at module initialization and computes `phys_to_virt` by adding the physical address in Rust. Previously each nested-page-table frame lookup crossed into a C `__va` helper. Two disposable-box hardware suites passed. A bounded exact-seed diagnostic covering 40 virtual seconds took 183.3 host seconds with this change, versus 225.8 and 221.3 seconds in baseline runs on the same box; entry cycles per exit fell from about 19.2–19.7k to 15.3k. The warm checkpoints varied, so these diagnostic spans are supporting evidence rather than an exact A/B.

The unmodified `bedrock-dst` binary then completed the full one-seed campaign with the direct-map change on the **same box as the 1,027-second baseline** (`box-2a8db29e`): the seed **passed** in 715 host seconds and the campaign in **872 host seconds** (4.13 seeds/hour), with no failures and timeline `tl-5595fa6e0585b75b`. This is about **15% less campaign wall time** than the baseline and still **13.4× the Intel CI campaign's 65 host seconds**. A second EPYC 4245P/HWE box (`box-7df741a2`) also passed the same seed, in 884 host seconds and 1,052 campaign seconds; that cross-box variation is why the same-box comparison is primary. The gain is general per-exit translation overhead reduction, while the remaining tens of millions of NPT and synthetic step exits still dominate.

A final diagnostic sampled one in 4,096 execute NPT faults over guest TSC 180–240 billion and retained 146 entries on the same hottest libc code page (its physical address changed across runs, so the sampler matched its 16-byte page start). ### NPT and instruction-trap design check (2026-10-14)

The VMCB's initialization-time `TLB_CONTROL=1` is overwritten in the actual SVM run path: each entry receives a fresh per-CPU ASID and requests a flush only when ASIDs wrap (or after an invalid VMRUN). Thus the initialization line is not a per-entry full-TLB flush to remove. Keeping one ASID while NPT execute permissions change would require explicit invalidation before reuse.

The [AMD APM's nested-paging permission model](https://docs.amd.com/api/khub/documents/sD1_QL~h4Afq2_tvzxqqSQ/content) has present, read/write, and NX controls, without independent read and execute backing mappings. GMET adds a guest-mode page execute check; it does not trap individual REP/RDRAND entries or provide extra address breakpoints. A shadow page containing software traps would therefore also change bytes visible to guest data reads unless a separate read-emulation or guest-code transformation mechanism were built. This rules out a simple NPT-only shadow-page shortcut. No production code or module was changed for this design check, and the **599 versus 65 host-second** comparison is unchanged.

### REP PMU behavior on the AMD test host (2026-10-14)

A userspace `perf_event_open` probe ran entirely on disposable `box-8ec16167` (EPYC 4245P, family 1Ah/model 44h, microcode `0xb404035`, Ubuntu kernel `6.8.0-146`). It performed 1,000 `REP MOVSB` copies per size, with an empty-loop baseline. AMD's retired-instruction event `0x0c0`, the event selected by the SVM counted path, added about **4,002 events** for every size from 1 through 4,096 bytes and 4,016 for 65,536 bytes. Three of those per copy are loop/register setup; the count is essentially independent of REP iteration count. `REP MOVSQ` showed the same pattern. AMD's retired-microcoded-instruction event `0x1c1` added exactly **1,000**, while retired microcode ops `0x1c2` ranged from **48,000** for 1-byte MOVSB copies to about **3.18 million** for 65,536-byte copies. The event names and meanings agree with [AMD's PMU documentation](https://docs.amd.com/api/khub/documents/eVy1a6TkWTouOo3krvItTA/content); Linux's [AMD raw-event encoding](https://github.com/torvalds/linux/blob/master/arch/x86/events/amd/core.c) places the high event digit in bit 32 of `perf_event_attr.config`.

With a 1,000-op `0x1c2` overflow period on a 1 MiB MOVSB, 16 recorded userspace signal contexts all had RIP at the REP instruction and a partially decremented RCX. Thus this host can interrupt a long REP mid-instruction using a microcode-op counter, but neither `0x0c0` nor `0x1c2` is a one-event-per-iteration deadline counter. The measured gap between signal contexts varied and includes interrupt delivery delay. A microcode-op overflow could serve as a coarse watchdog only after a sound upper bound on REP progress before the trap is established; these host userspace measurements do not establish its behavior under SVM or justify removing REP breakpoints or charging one tick for a whole REP. No Bedrock module was built or loaded for this probe. Source, output, and host identification are ignored under `target/boxctl-evidence/box-8ec16167/rep-pmu/`.

### Partial-REP retirement detector feasibility (2026-10-14)

An AMD [IBS execution sample](https://docs.amd.com/r/en-US/68658-uProf-getting-started-guide/Introduction-to-IBS-Instruction-Based-Sampling) tags a selected micro-op at dispatch and records it after retirement; it is a sample, not an exhaustive instruction stream. Another idea was to run pages without REP breakpoints, use `PMCx1C1` (retired microcoded instructions) to detect a REP afterward, and replay the batch. That is not a safe shortcut: this SVM run path has no transaction or undo log for arbitrary guest memory writes, and a partially completed REP can change memory before its instruction retires.

To check the hardware signal, a userspace `perf_event_open` probe on disposable `box-eb6ed107` (EPYC 4245P, family 1Ah/model 44h, Ubuntu `6.8.0-146`) armed `PMCx1C2` (retired microcode ops) for overflow during a 1 MiB `REP MOVSB`, then read `PMCx1C1` from the signal handler. All 16 observed signals had RIP still at the REP instruction and partially decremented RCX. The first trial of each invocation read four microcoded instructions, likely setup noise; the other **14 of 16 read zero**. This agrees with [AMD's definition](https://docs.amd.com/api/khub/documents/eVy1a6TkWTouOo3krvItTA/content) of `PMCx1C1` as *retired* microcoded instructions: it cannot reliably announce an in-progress REP before its writes. The already measured `PMCx1C2` overflow can interrupt mid-REP, but does not reveal the starting RCX if execution reached REP from an untrapped, unknown path. Neither counter justifies removing entry breakpoints or assuming one tick per REP. The probe did not build or load any Bedrock module. Source, raw readings, and box identity are ignored under `target/boxctl-evidence/box-eb6ed107/rep-partial/`; the box was deleted. The performance comparison remains **599 versus 65 host seconds**.

A separate source review considered replacing the four reachable `RET` breakpoints on the hot libc copy path with a write guard on its return-address page. The small-copy disassembly leaves RSP unchanged, and a nested-page write guard would cover physical aliases of the return word. But the existing single-page execution plan would still take an execute NPT fault at the return target; freeing breakpoint slots helps only if a multi-page plan also proves safe reentry to the copy page. In the earlier hot-page sample, only 34 of 137 faults looked like returns. Even eliminating every such return-related fault on that page would address roughly 4% of the sampled **all-page** faults (34/137 × 1.86M/11.43M), assuming that sample is representative. The return guard alone is therefore not a high-leverage next implementation, and no code or module was changed for this check.

### Microcode-op count invertibility (2026-10-14)

A second userspace-only probe on disposable `box-41f45515` (EPYC 4245P, family 1Ah/model 44h, Ubuntu `6.8.0-146`) counted AMD [`PMCx1C2` retired microcode ops](https://docs.amd.com/api/khub/documents/eVy1a6TkWTouOo3krvItTA/content) for 1,000 `REP MOVSB` copies per measurement. Across three trials at each size and destination/source offsets 0, 1, 7, and 31, every size from **1 to 127 bytes** produced the same **48,000-event** delta at aligned offset 0 (48 per copy). The same collision appeared at the other offsets. At offset 31, 128 and 129 bytes both produced **80,000** events. Some measurements around 129 bytes varied across trials. Thus the microcode-op total is neither a one-event-per-iteration count nor an injective encoding of copy length, even for a single known REP site. It cannot reconstruct the missing virtual ticks when a global batch reaches REP with unknown starting RCX. The exact tab-separated results, source, and box identity are ignored under `target/boxctl-evidence/box-41f45515/rep-op-count/`; the box was deleted. No module was built or loaded, and the **599 versus 65 host-second** comparison is unchanged.

Source review also confirmed that the global counted path already leaves independently proven hazard-free code pages executable: `trust_npt_code_4k` makes those leaves read-only and clears NX, while the global run path grants temporary execute permission to its selected pages. The smaller page-batch path temporarily restricts other pages. Consequently, broadening trusted-page residency in the global path would duplicate existing behavior rather than address its dominant hazardous-page faults. A proposed trusted-page fault diagnostic worktree was removed without building or running a module.

## Intel-equivalent completed-REP retirement (2026-10-14)

Intel Bedrock uses programmable PMC0 event `INST_RETIRED.ANY_P` (`0xC0`) for
guest virtual time; fixed counter 0 is reserved for PEBS. A userspace probe
of the exact raw `0xC0` event on the Intel Tempo CI runner (Xeon Platinum
8488C) measured 1,000 extra retirements for 1,000 completed `REP MOVSB`
instructions for lengths 1, 64, 512, 4,096, and 65,536 bytes, apart from
occasional interrupt-noise samples. See [the Intel metal run](https://github.com/tempoxyz/bedrock/actions/runs/38621867982).
Thus a completed REP consumes one Intel virtual tick regardless of iterations.

The AMD candidate makes recognized `F3 MOVS/STOS` entries execute in bounded
native chunks, charges a virtual tick only on completion, and removes those
entries from global code-page hazards. Other repeated string forms remain
hazards. It keeps global batches away from a REP *entry*, while a global batch
may reach REP and count its retirement with IRPERF. A targeted 100-NOP plus
5,000-byte `REP STOSB` case reached its exact deadline at virtual tick 101,
with RIP after REP and RCX zero. The resumed-RF/page-crossing deadline test,

### Wider guarded-leaf alias filters (2026-10-14)

An isolated walker profile on disposable `box-bf56e678` (EPYC 4245P, HWE `7.0.0-38-generic`) split 5.41 billion measured alias-walk cycles in an early seed window: **4.01 billion** scanning 1.65 million raw leaf tables, 0.59 billion traversing cached upper tables, 0.57 billion scanning raw upper tables, and 0.24 billion skipping 8.33 million leaf tables through the existing Bloom filter. Its ten-virtual-second campaign hit the known `E4/graceful-stop` assertion, so the cycle breakdown is diagnostic evidence rather than a workload pass.

The guarded-leaf Bloom filter was widened from 256 to 1,024 bits. This adds **288 KiB per VM** across active and cached filter arrays. The focused membership/saturation test, all 272 VMX tests, and the disposable-box SVM suite passed. In alternating exact pinned one-seed campaigns on the same box, the widened filter passed in **236 and 245 host seconds**, while the clean module passed in **253 and 267 seconds**. Warm checkpoints varied, but the seed portion was also faster in both candidate runs. All four full verdicts passed, using identical guest assets and the same userspace driver SHA-256 `08715a38504521806f70f2bcb518b501353db80c21f697b9138adc75930befb2`. This is an observed workload improvement, not a claim of a fixed percentage across hosts or guests. The change was merged into `dan/amd-tempo-dst`; logs are ignored under `target/boxctl-evidence/box-bf56e678/`. Kernel modules were built and loaded only in the disposable box.
